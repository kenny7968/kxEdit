# 「選択範囲のみ」スコープの陳腐化を検出する — 設計書

- 日付: 2026-08-06
- 対象: `src/yEdit.App/SearchController.cs`
- 出自: PR #37 の申し送り **S-7**(および受容項目 A-1 / A-6)

## 0. 要旨

`SearchController._selectionScope` は「選択範囲のみ」トグル ON 時に捕捉した
char 位置の組 `(Start, End)` である。捕捉後は**文書内容の変化を一切追跡しない**ため、
捕捉と「すべて置換」の間に編集が入ると、**ユーザーが選択していない範囲へ置換が及び、
しかも「N 件置換しました」と成功発声する**。

本設計は、スコープに**捕捉元の `TextSnapshot` 参照**を持たせ、使用時に参照同一性で
陳腐化を検出して**拒否**する。破壊は起きず、SR には状態が正しく伝わる。

## 1. 調査 — S-7 の記述は経路を取り違えていた

PR #37 の申し送り S-7 は次のように書いていた。

> `_selectionScope` / `_lastHit` がタブクローズで持ち越される。修正は `DocumentClosed` の
> 購読で 2 つも落とす **1 行**。

これを実測で検証したところ、**2 点とも成立しなかった**。

### 1.1 タブクローズ経路は再現しない

`DocumentManager.cs:59` と `MainForm.cs:954` は「選択タブ削除時の `TabControl.Selected`
発火は WinForms の仕様上保証されない」と記す。これが真なら、アクティブタブを閉じても
`ActiveDocumentChanged` が発火せず `_selectionScope` が持ち越される。

探針テストで**タブ数 1 / 2 / 3 × 閉じる位置 先頭 / 中間 / 末尾 の 6 通り**を測ったところ、
**全ケースで `ActiveDocumentChanged` が 1 回発火した**(.NET 9 / WinForms `TabPages.Remove`)。
既存の `ActiveDocumentChanged` ハンドラが `_lastHit` / `_selectionScope` を落としているため、
S-7 が主張した実害はこの経路では発生しない。

再現を試みた探針テストの結果も「選択範囲がありません」であり、置換は起きなかった。

### 1.2 提案された「1 行修正」は有害

`DocumentClosed` で無条件に `_selectionScope` を落とすと、**非アクティブタブを閉じたとき**に
まだ生きているアクティブ文書の**正当なスコープを破壊する**(`DocumentClosed` は閉じた文書に
関係なく発火し、非アクティブタブのクローズでは切替自体が起きない)。
S-7 の指示をそのまま入れると新たな不具合になる。

### 1.3 しかし実害そのものは別経路で実在する

S-7 が予言した被害は、**タブクローズではなく捕捉後の編集**で起きる。探針で再現した。

```
本文 "abc abc"
  後半 [4,7) の "abc" を選択 → 「選択範囲のみ」ON(スコープ [4,7) を捕捉)
  先頭に "QQQQ" を入力 → 本文 "QQQQabc abc"
  「すべて置換」(abc → X)

実測結果:  本文 "QQQQX abc"     発声「1 件置換しました」
```

ユーザーが選択したのは**後半**の `abc`。実際に置換されたのは**前半**の `abc`
(挿入で位置がずれ、偶然 `[4,7)` に入った)。選択した箇所は無傷のまま、
**選択していない箇所が書き換わり、成功発声が出る**。SR ユーザーには区別がつかない。

同一タブでバッファを差し替えた場合(開き直し・復元・EOL 変換相当 = 受容項目 A-1)も
同じ状態になる。探針では「見つかりません」に落ちたが、これは差し替え後の
`[0,3)` にたまたま一致が無かっただけで、内容次第で置換に化ける。

文書が**縮んだ**場合(受容項目 A-6)はクランプに救われることを確認した
(`[0,15)` 捕捉 → 3 文字へ縮小 → `ReplaceCharRange(0, 15, ...)` がクランプされ正常終了)。
A-6 の受容理由が「新文書が短い場合だけ正しい」とされたのはこのとおりである。

### 1.4 真因

`_selectionScope` が**捕捉時点の絶対 char 位置で固定され、以後の文書変更と結び付いていない**。
タブクローズは症状の一経路にすぎず、`DocumentClosed` を触っても真因には届かない。

## 2. 方針

スコープを**捕捉元の文書内容に紐付ける**。使用時に紐付けが切れていたら使わない。

`TextSnapshot` は編集のたびに新インスタンスになり、キャレット・選択の移動では変わらない。
これは求める粒度と完全に一致する(「選択が find 移動でクロバーされても捕捉は生きる」という
捕捉方式の元の目的を壊さない)。参照同一性による世代判定は
`TextBuffer.Modified`(`ReferenceEquals(_current.Root, _savedRoot)`)および
`MaterializedSearchStrategy` のキャッシュ判定が既に採る本リポジトリの idiom である。

`TextSnapshot.Root` は `internal`(`yEdit.Core`)のため App 層からは触れない。
App は `TextSnapshot` インスタンス自体を保持して比較する。

### 2.1 検討して採らなかった案

| 案 | 却下理由 |
|---|---|
| 編集に追従してスコープを移動(アンカー追跡) | スコープ内削除・スコープ跨ぎ編集・Undo など境界事例が多く、実装とテストが数倍になる。ユーザー体験は最も自然だが、本件の主目的(破壊の停止)には過剰 |
| 陳腐化したら現在の選択で取り直す | 直前に「次を検索」していると選択はヒット位置なので、**ヒット 1 個だけが対象**になる誤爆を生む。捕捉方式を導入した元の理由と衝突する |
| 文書変更イベントを新設して先行無効化 | `EditorControl` に新しい event = 新しい seam。`UpdateUI` はキャレット移動でも発火するので流用不可(捕捉方式の目的を壊す)。PR #37 が seam を 2 つ足した直後でもあり、参照保持で足りる本件に seam は割に合わない |

## 3. 実装

### 3.1 データ構造

```csharp
// 変更前
private (int Start, int End)? _selectionScope;
// 変更後
private (TextSnapshot Snap, int Start, int End)? _selectionScope;
```

`using yEdit.Core.Buffers;` を追加(新規アセンブリ依存なし。`SearchController` は既に
`ed.CurrentBuffer.Current` を扱っている)。

### 3.2 捕捉 — `OnInSelectionToggled`

```csharp
if (on && ActiveEditor is { } ed)
{
    var (s, e) = ed.GetSelectionCharRange();
    _selectionScope = e > s ? (ed.CurrentBuffer.Current, s, e) : null;
}
```

### 3.3 使用 — `ReplaceAll`

`snap` は既存コードが `ed.CurrentBuffer.Current` から取っているものをそのまま使う。

```csharp
if (_selectionScope is not { } scope)
{
    Announce("選択範囲がありません");
    return;
}
if (!ReferenceEquals(scope.Snap, snap))
{
    _selectionScope = null; // 陳腐化したら捨てる(古いピース木の参照を即解放)
    Announce("選択範囲が変わりました。選択し直してください");
    return;
}
```

拒否時に `null` を入れる理由は、**古い `TextSnapshot` が指すピース木の参照を即座に手放す**ため。
副作用として 2 度目の「すべて置換」は既存文言「選択範囲がありません」になるが、
その時点でスコープは実際に存在しないので発声は正確である。

### 3.4 触らないもの

- **`DocumentClosed` の購読** — §1.2 のとおり無条件リセットは有害。かつ別文書は
  別スナップショットなので §3.3 の判定が自動的に覆う。
- **`DocumentManager.cs:59` / `MainForm.cs:954` の防御的コメントと実装** — 6 通りの
  観測は WinForms の仕様の証明にならない。防御は残し、実測値のみ本書に記録する。
- **`_lastHit`** — 使用箇所(`Find`)は `selStart == h.Start && selEnd == h.End` が
  成り立つときだけ歩進に使う。編集後に選択が偶然一致しない限り効かず、
  効いた場合も影響は「次の 1 件を飛ばす」に留まりデータは壊れない。本件の対象外。
- **`UpdateCount`** — スコープを参照せず常に全文を数える。影響なし。
- **`Dismissed` の購読** — スコープを落とす追加は保持量には効くが、
  ダイアログを閉じて開き直したときにスコープが消える**挙動変更**になる。
  本 PR の目的外。§6 の申し送りへ。

## 4. 保持量

スコープ捕捉中は `TextSnapshot` 1 本を強参照する。解放されるのは
再トグル(`OnInSelectionToggled`)・文書切替/クローズ(`ActiveDocumentChanged`)・
陳腐化拒否(§3.3)の 3 経路。

ピース木は永続データ構造でノードを共有するため、編集後に旧スナップショットが
固定する増分は通常小さい。ただし本文を全置換した直後などは旧木がまるごと残りうる。
上限はアクティブ文書 1 本ぶんで、`MaterializedSearchStrategy` のキャッシュと同じ桁。

### 5.1 実装時の追記(最終レビューを受けて)

設計時に想定していなかった事実が 3 件出たので記録する。本節は実施記録であり、
§1〜§5 の策定内容は書き換えていない。

- **保持を弱参照へ変更した。** §4 は保持量を「アクティブ文書 1 本ぶん」と見積もったが、
  同一タブのバッファ差し替え(`ReplaceSource` = 開き直し・復元・混在 EOL の保存)では
  `ActiveDocumentChanged` が発火せず、旧ピース木が次の置換まで残る。レビューは
  `DocumentClosed` へ条件付きの解放を足す案を出したが、**それではこの実証済み経路が塞がらない**。
  `WeakReference<TextSnapshot>` にすると全経路で保持がゼロになり、判定は変わらない
  (捕捉元が生きていれば必ず現在のスナップショットと同一。回収済みなら拒否=安全側)。
- **置換成功後にスコープを取り直す処理を足した。** §3 のままだと「範囲を選んで語を変えながら
  何度か置換する」ワークフローが 2 回目で拒否される。修正前はここが通っていたが、
  それはずれた範囲で走っていただけで正しさの根拠にはならない。とはいえ現実的な使い方であり、
  置換後の範囲は `fragment` の長さから厳密に決まるので取り直す。
- **`TextBuffer.Modified` と「同じ idiom」ではなかった。** `Modified` はピース木の `Root` を
  比べるが、`Undo` は同じ `Root` を**新しい** `TextSnapshot` で包み直す
  (`TextBuffer.cs` の `Undo`)。よって `Modified` は Undo で `false` に戻るのに対し、
  本ガードは戻らない。`TextSnapshot.Root` は `internal` で App から見えないため
  現実装が唯一の選択肢であり、内容が同一でも拒否するのは安全側の差。テストで固定した。

## 6. 申し送り

- `Dismissed`(検索終了)でスコープを落とすか。保持量には効くが挙動変更を伴う(§3.4)。
- `DocumentManager` / `MainForm` の「`TabControl.Selected` は保証されない」という記述の
  扱い。本書 §1.1 に 6 通りの実測を記録したが、防御的実装は残してある。
- **`ReplaceOne`(単発の「置換」)は `_selectionScope` も `d.InSelection` も参照しない。**
  したがって「選択範囲のみ」を ON にしていても、単発の「置換」は選択範囲外のヒットを置換する。
  main と挙動同一で本件由来ではないが、「SR ユーザーには区別がつかない」系の非一貫性として
  同じ系統に属する。最終レビューで発見(実装時追記)。

## 7. L5 判定
