# 複数インスタンス起動の禁止(単一インスタンス化) 設計書

- 日付: 2026-09-14
- 対象 Issue: なし(Issue 起票はせず docs/plans に設計書と実装計画を残す運用。ユーザー承認 2026-09-14)
- ブランチ: `feature/single-instance`

## 1. 背景と目的

kxEdit は現在、多重起動を一切制御していない。`kxEdit.exe` を 2 回起動すれば 2 つのプロセスが
並走し、どちらも同じ `%APPDATA%\kxEdit` 配下の設定・バックアップ・セッション状態を書く。

これは既知の穴で、`docs/plans/` に **M9+ の申し送り**として繰り返し記録されてきた。

| 記録 | 内容 |
|---|---|
| `2026-06-26-m5-backup-design.md` | 複数インスタンス同時起動時のバックアップ競合(単一インスタンス前提・要申し送り) |
| `2026-07-19-security-hardening-medium-low.md` BK-M-2 | インスタンス B の「すべて破棄」がインスタンス A のライブバックアップを消す(friendly-fire DoS)。「単一インスタンス Mutex が存在しない(検証: `grep Mutex` on App が空)」と明記されている |
| `2026-07-23-unified-session-restore-design.md` | `session-state.json` は last-writer-wins。adopt-move が他インスタンスのバックアップを物理的に引き抜きうる(Task 4 脆弱性レビュー指摘 1・受容済み) |

**目的**: インスタンスが無ければ新規起動し、既に在れば重複起動せず既存インスタンスへ
フォーカスを移す。上記の競合群を通常運用から取り除く。

## 2. 決定事項(ブレインストーミング 2026-09-14)

| # | 論点 | 決定 |
|---|---|---|
| D1 | 2 つ目を検出したときのユーザー体験 | **無言で終了し、既存ウィンドウを前面化+復元**。ダイアログも SR 通知も出さない(一般的なエディタと同じ挙動。毎回の操作コストを増やさない) |
| D2 | 「1 インスタンス」のスコープ | **ログオンセッション単位**(`Local\` 名前空間)。別ユーザー / 別 RDP セッションでは別々に起動できる |
| D3 | 意図的な 2 つ目起動の抜け道 | **コマンドライン引数 `--new-instance`** |
| D4 | 既存インスタンスが応答しないときの扱い | **エラーを表示して 2 つ目は終了**(フォールバック起動はしない) |
| D5 | 実現方式 | **名前付き Mutex + 名前付きパイプ** |

### D2 の理由(なぜユーザー単位・マシン単位にしないか)

「フォーカスを移せる範囲」と「ファイルが衝突する範囲」がズレている。設定・バックアップ・
セッションは `%APPDATA%` = ユーザー単位で共有されるが、**ウィンドウの前面化はログオン
セッションをまたげない**(別セッションのウィンドウは物理的に前面化できない)。

ユーザー単位(`Global\` + SID)にすると、同一ユーザーが 2 セッションにログオンしている場合に
「起動もしないし、何も起こらない」状態が生まれる。D1 で決めた「無言で既存にフォーカス」が
成立しない死角であり、SR ユーザーには特に酷い。同一ユーザーの多重ログオンは稀なケースとして
受容する(§7)。

### D4 の理由(なぜフォールバック起動しないか)

引き渡し失敗は既存インスタンスのハング・クラッシュ前後に集中する。そこで 2 つ目を起動すると
「ハングした A + 新規 B」がバックアップを奪い合う、本設計が塞ごうとしている最悪の組み合わせを
作る。詰みを避けるための保険が、いちばん危険な瞬間に働く形になっている。

エラー文言は対処を含める:
「kxEdit は既に起動していますが応答しません。タスク マネージャーで終了してから再実行してください。」

### D5 の理由(検討した他案)

| 案 | 却下理由 |
|---|---|
| Mutex + `WM_COPYDATA` | 相手ウィンドウの探索に `EnumWindows` 等の P/Invoke が要る。**昇格状態が違うと UIPI に無言でブロックされる**(D4 の「必ずエラーを出す」と噛み合わない)。実ウィンドウ無しでは検証できず自動テストが薄くなる |
| `WindowsFormsApplicationBase` (`SingleInstance = true`) | コード量は最小だが**起動シーケンスを丸ごと奪う**。`Program.Main` は「最初のウィンドウ生成より前に IME 推測を無効化する」順序が IL テスト `ProgramMain_suppresses_ime_mode_inference_before_creating_any_window` で固定されており、`Application.Run` を内部で呼ぶこの方式と正面衝突する。`CrashHandler` / `SetUnhandledExceptionMode` の配線も差し替えが必要。**プロジェクト最大の不変条件(IME 余計発声の抑止)を人質に取る** |

Mutex + 名前付きパイプは、将来のファイル引数受け渡し(§6)がメッセージにパスを載せるだけで
乗る点も決め手になった。

## 3. 起動シーケンスと配置

`Program.Main` を `Main(string[] args)` に変え、排他ゲートを次の位置に挿す。

```
1. ImeStartup.SuppressWinFormsImeModeInference()   ← 現状のまま最初の文(不変条件)
2. EncodingCatalog / Trace ログ                     ← 現状のまま
3. ★ SingleInstanceGate.Acquire(args)              ← 新規。ここで 2 つ目は終了する
4. PreviewUserDataSweeper.SweepIfSoleInstance()
5. ApplicationConfiguration.Initialize() 以降        ← 現状のまま
```

### なぜ ImeStartup より後なのか

「IME 推測の無効化は最初のウィンドウ生成より前」という不変条件が IL テストで固定されている。
ゲートの失敗経路(D4)は `MessageBox` を出す = ウィンドウが出る経路なので、ゲートを前に置くと
この不変条件を文面上またぐ。`ImeStartup` は**プロセス内のリフレクションテーブルを塗るだけで
共有状態に触れない**ため、2 つ目のプロセスが数ミリ秒これを実行してから終了しても実害はない。
不変条件を literal に保つ側へ倒す。

### なぜ `PreviewUserDataSweeper` / `SettingsStartup.Prepare` より前なのか

こちらは逆に**共有状態を書き換える**。特に `SettingsStartup.Prepare` は壊れた
`settings.json` を**退避(quarantine)** する。2 つ目のプロセスにこれを実行させると、
ゲートで弾く前にユーザーの設定ファイルを動かしてしまう。

この順序は IL テストで固定する(§5)。理由が「共有状態を触る前に弾く」である以上、
黙って入れ替わると設定ファイル退避の事故に戻る。

### ゲートの 3 状態

| 結果 | 次の動作 |
|---|---|
| `FirstInstance` | Mutex を保持したまま通常起動。パイプ待ち受けを開始 |
| `HandedOff` | 引き渡し成功。**無言で終了**(終了コード 0) |
| `HandoffFailed` | エラーを表示して終了(終了コード非 0) |

### Mutex の寿命

`Mutex` をローカル変数に置くと GC がファイナライズして解放しうる。プロセス寿命と一致させる
(静的フィールドで保持し、`Application.Run` を `using` で囲む)。

### 引数の扱い(今回の範囲)

`--new-instance` のみ解釈し、**未知の引数は無視して Trace に残す**。将来ファイルパスを受ける
ときに、今日の実装が「未知の引数でエラー終了する」形だと後方非互換になるため。
ファイルを開く処理自体は今回やらない(§6)。

## 4. 引き渡しプロトコル

### 名前

| 種別 | 名前 | 根拠 |
|---|---|---|
| Mutex | `Local\kxEdit.SingleInstance.<ユーザーSID>` | `Local\` = **TS セッション**単位。SID も足してユーザー単位にも切る(下記の訂正を参照) |
| パイプ | `kxEdit.SingleInstance.<セッションID>.<ユーザーSID>` | **パイプ名前空間は OS 全体で共有**され `Local\` の概念がない。セッション ID と SID を名前に含めて手動でスコープを作る |

#### 【Task 3 仕様レビューによる訂正 2026-09-14】Mutex 名にも SID を入れる

策定時は Mutex 名を `Local\kxEdit.SingleInstance`(SID なし)としていた。これは誤りで、
**同一セッションで別ユーザーとして起動すると起動時クラッシュする**。

**用語の訂正**: 本設計書が当初「ログオンセッション単位」と書いていたものは、正しくは
**TS セッション単位**である。実測(`NtQueryObject(ObjectNameInformation)`)で、
`Local\foo` は `\Sessions\<TS セッション ID>\BaseNamedObjects\foo` に解決される。
この ID は `Process.SessionId` と同じ値で、**ログオンセッション(`S-1-5-5-X-Y`)とは別物**。
1 つの TS セッションに複数のログオンセッションが同居しうる —— その差が本欠陥の温床だった。

**欠陥の内容**: 同一 TS セッションで別ユーザーになる経路は現実にある
(`runas /user:other`、および**管理者の資格情報を入力する UAC 昇格** —— 管理者アカウントと
常用アカウントを分けている環境では日常的)。このとき Mutex 名は衝突するのにパイプ名は
衝突しない。さらに `Local\` Mutex の既定 DACL には**別ユーザーの ACE が 1 つも無い**ため、
`new Mutex(initiallyOwned: true, name, out createdNew)` は `MUTEX_ALL_ACCESS` を要求して
`UnauthorizedAccessException` になる(実測で再現)。結果、2 人目のユーザーの kxEdit は
**D4 のエラーダイアログすら出せずに起動時例外で落ちる**。D4 の不変条件をゲート自身が破る。

**なぜ SID を足すのが D2 と矛盾しないか**: D2 が却下したのは `Global\` + SID
(セッションをまたぐ)であって、`Local\` + SID ではない。D2 の原理は
「**フォーカスを移せる範囲 ∩ ファイルが衝突する範囲**」をスコープにすることだった。
同一セッションの別ユーザーは、ウィンドウが同じデスクトップにあるので**前面化でき**、
`%APPDATA%` は別なので**衝突しない**。よって別インスタンスとして起動してよく、それは
「TS セッション ∩ ユーザー」= **元々のパイプ名のスコープ**である。
つまり**パイプ名の方が D2 を正しく実装しており、Mutex 名がズレていた**。

| 案 | 実スコープ | 「別セッションで何も起きない」死角 |
|---|---|---|
| `Global\` + SID(D2 で却下) | ユーザー単位(セッションをまたぐ) | **あり** |
| `Local\` 単独(策定時) | TS セッション単位(ユーザーをまたぐ) | なし。ただし別ユーザーでクラッシュ |
| **`Local\` + SID(訂正後)** | **TS セッション ∩ ユーザー** | **なし** |

**副次効果**: 名前が別になるので、上記 `UnauthorizedAccessException` の経路自体が消滅する。

### 流れ

```
B(2つ目)                                A(既存)
  │ Mutex 取得失敗 → 自分は2つ目            │ Mutex 保持・パイプ待受中
  │                                         │
  ├─ Connect(timeout: 3s) ─────────────────▶│
  ├─ GetNamedPipeServerProcessId() で A の PID を取得
  ├─ A の実行ファイルパスが自分と一致するか検証 ★3
  ├─ AllowSetForegroundWindow(A の PID) ★1  │
  ├─ 要求を送信 ───────────────────────────▶│
  │                                         ├─ UI スレッドへマーシャル
  │                                         ├─ 最小化なら SW_RESTORE
  │                                         ├─ GetLastActivePopup → SetForegroundWindow ★2
  │◀────────────────────── ACK 送信 ────────┤
  └─ ACK 受信後に終了                        │
```

★ の 3 点が、素朴な実装だと確実に壊れる箇所である。

**★1 フォアグラウンド権の受け渡し**: Windows は任意のプロセスによる `SetForegroundWindow` を
拒否する。前面化できるのは**今まさにユーザーが起動した B の方**なので、B が
`AllowSetForegroundWindow(A の PID)` で権利を A へ譲渡してから依頼する。省くと A のタスクバー
ボタンが点滅するだけで前面に出ない。**B が ACK を待たずに終了すると譲渡した権利ごと消える**
ため、ACK 待ちは飾りではなく必須。

**★2 モーダルダイアログの吸い込み**: A が設定ダイアログ等を開いている最中に来た場合、
メインフォームを前面化すると**モーダルに入力を吸われて操作不能に見える**。
`GetLastActivePopup` で現在有効な最前面の子ウィンドウを求め、そちらを前面化する。

**★3 パイプのなりすまし検証**: パイプ名前空間は OS 全体共有なので、悪意あるプロセスが
先回りして同名パイプを作れる。今日は空メッセージなので実害はないが、**将来ファイルパスを
送るようになった時点で情報漏洩になる**ため、最初から接続先プロセスの実行ファイルパスを検証する。
逆向き(A がパイプを作れなかった場合)は、A は待ち受けなしで通常起動を続け Trace に警告を残す。
以後の起動は D4 のエラーになるが、**攻撃者へデータが渡らない**方向へ倒れる。
サーバ側のパイプ ACL は現在のユーザーのみに制限する。

### 【実装計画時の精密化 2026-09-14】失敗理由を 2 つに分ける

★3 の検証を素直に実装すると、**別フォルダに展開した別ビルドの kxEdit** も「実行ファイルパスが
違う」ため引き渡し拒否になる。このとき D4 の文言「応答しません」を出すのは誤診である
(相手は正常に動いている)。そこで `HandoffFailed` を 2 つに分ける:

| 結果 | 文言 |
|---|---|
| `NoResponse` | 「kxEdit は既に起動していますが応答しません。タスク マネージャーで終了してから再実行してください。」 |
| `ForeignPeer` | 「別の場所にある kxEdit が既に起動しています。先に終了してから実行してください。」 |

`ForeignPeer` は誤診の回避であると同時に、**D3 の動機だった「修正版を起動したつもりが旧版を
触っていた」取り違えを能動的に検出して伝える**経路になる。黙って旧版を前面化するより望ましい。
意図的に 2 ビルドを並べたい場合は `--new-instance` を使う。

### 2 つのレース

**起動中レース**: A が Mutex 取得済みだがパイプ待受開始前に B が来る。
→ A は **Mutex 取得直後・`MainForm` 構築より前**に待受を開始する。`MainForm` の構築は重いので
ここを後ろに置くと窓が広がる。ウィンドウがまだ無い時点で来た要求は保留し、`MainForm.OnShown`
で消化する(今日は「どのみち前面に出る」ので実質 no-op だが、将来のファイル引数では
取りこぼしが実害になる配線である)。B 側の 3 秒タイムアウトもこの窓を吸収する。

**終了中レース**: A が終了処理中で、Mutex はまだ保持しているがパイプは閉じた。
→ B は接続失敗時に **Mutex 取得を 1 回だけ再試行**し、取れたら自分が 1 つ目として起動する。
これが無いと、A を閉じた直後の再起動が「応答しません」エラーになる。

**A のクラッシュ**: Mutex は最後のハンドルが閉じた時点で OS が破棄するため、次回起動は
`createdNew = true` になり自己回復する。

## 5. コンポーネント分解とテスト戦略

### 分解(すべて `kxEdit.App`)

| 型 | 責務 | テスト可能性 |
|---|---|---|
| `SingleInstanceGate` | 3 状態の判定と分岐。Mutex / パイプ名を**注入可能**にする(テストが実名を使うと並列実行で相互干渉する) | ○ 実パイプで往復可能 |
| `SingleInstanceServer` / `SingleInstanceClient` | 待ち受けループ・接続・ACK・タイムアウト | ○ ウィンドウ不要 |
| `SingleInstanceRequest` | メッセージの直列化 / パース。**今日は空でも型として置く**(将来ファイルパスが乗る器) | ◎ 純粋関数 |
| `CommandLineOptions` | `--new-instance` の解釈、未知引数の無視 | ◎ 純粋関数 |
| `WindowActivator` | `GetLastActivePopup` / `ShowWindow` / `SetForegroundWindow` の薄いラッパ | ✕ 実ウィンドウ必須 → L5 |

**分解の意図**: Win32 に触る部分を `WindowActivator` 1 点に押し込め、それ以外を
「実ウィンドウなしで検証できる側」に寄せる。この分離をしないと、単一インスタンス機構全体が
「手で動かすしかない」塊になる。

### 層別の担当

| 層 | 内容 |
|---|---|
| **L3**(`kxEdit.App.Tests`) | 一意な名前でサーバ/クライアントを立て、往復・ACK・接続タイムアウト・終了中レースの再試行を実測。引数パースと名前生成は純粋関数として単体で |
| **L3 (IL)** | `Main` の IL 上で**ゲートの呼び出しが `PreviewUserDataSweeper` / `CreateMainForm` より前**であることを固定(既存 `IlCallees` 方式を流用) |
| **L5**(実機 SR・手動) | ①最小化からの復帰 ②モーダルダイアログを開いた状態での引き渡し ③引き渡し後に SR が新しいフォーカスを読むか ④`--new-instance` で 2 つ目が起動するか |

**L5 は必須**と判断する。フォアグラウンド移動は SR の読み上げ対象そのものを変える操作であり、
UIA 経路に触れないリファクタとは性質が違う。特にモーダル中の引き渡しは、過去に踏んだ
「モーダルの吸い込み」と同じ失敗の形をしている。

**ミューテーション検証は原則行わない。** 本機能の中核はプロセス間 I/O とイベント配線であり、
CLAUDE.md §4A で禁止されている領域(ファイル入出力・イベントマッピング)に該当する。

> 【実施時の精密化 2026-09-14】**純粋関数の 3 型だけは例外として対象にする** ——
> `CommandLineOptions` / `SingleInstanceRequest` / `SingleInstanceNames`。
> いずれも I/O を持たない文字列処理であり、かつ**他プロセス・他ビルドとの契約**
> (ワイヤ形式・Mutex 名・パイプ名)を表現している。契約がドリフトしても単一ビルド内の
> テストは全緑のままなので、ユーザー CLAUDE.md の「厳密な挙動を保証する必要がある場合にのみ許可」に
> 該当すると判断した。実際、この例外運用で Task 1 / 2 / 3 それぞれに生存変異が見つかり、
> いずれも「テストが定数から自己無矛盾に導出されていて契約を固定していない」という同じ形だった。
> **Task 4 以降(パイプ送受信・ゲート・Win32)には適用しない。**

### 脆弱性レビュー

CLAUDE.md §3 の前倒しレビュー条件(外部入力のパース・プロセス起動)に該当するため、
該当タスク時に**脆弱性レビューを実施**する。焦点は ★3(なりすまし検証)・パイプ ACL・
引数パース。

## 6. 非スコープと将来の接続

### 今回やらないこと

- **ファイル引数で実際にファイルを開く**。器(`SingleInstanceRequest`・引数パース)だけ用意し、
  開く処理は別機能として後日。
- **ファイル関連付けの登録**(レジストリ / インストーラ)。配布は zip 展開のみのため別議題。

### 将来のファイル引数対応がどう乗るか

1. `CommandLineOptions` がファイルパスを拾う。
2. 1 つ目なら起動後にそのパスを開く。
3. 2 つ目なら `SingleInstanceRequest` にパスを載せて送る。A が受けて開く。
   保留キュー(§4 起動中レース)がそのまま取りこぼし防止として働く。
4. ★3 のなりすまし検証が、このときに初めて実効的な意味を持つ。

## 7. 副次効果と受容するリスク

### 副次効果(意図した波及)

§1 に挙げた M9+ 申し送りの競合群が、通常運用では発生しなくなる。

**ただし、これらに対する既存の防御は一切撤去しない。** `--new-instance` と別ログオン
セッションでは複数インスタンスが依然成立するため、セッション GUID サブディレクトリによる
バックアップのスコープ分離も `PreviewUserDataSweeper.SweepIfSoleInstance` も現状のまま残す。
「単一インスタンスになったから不要」という簡略化は、抜け道を自分で用意した以上成り立たない。

### 受容するリスク

| リスク | 判断 |
|---|---|
| 同一ユーザーが複数セッション(コンソール + RDP)にログオンすると 2 つ起動でき、`%APPDATA%` を共有して競合する | D2 の帰結として受容。別セッションのウィンドウは前面化が物理的に不可能で、防ぐと「何も起きない」死角になる |
| 同一セッションの悪意あるコードが Mutex 名を先取りして kxEdit の起動を妨害できる | 同一ユーザー権限のコードは既に任意の操作が可能なため、新たな攻撃面ではない |
| `--new-instance` を使うと上記の競合問題が復活する | 開発・検証用の明示的な抜け道。説明書には載せない |
| **昇格の順序**: 同一ユーザーが管理者として先に起動し、その後に通常権限で起動すると、SID もセッションも同じなので**名前が完全に一致する**。高 IL プロセスが作ったオブジェクトには既定で High / NO_WRITE_UP の必須整合性ラベルが付き、`MUTEX_MODIFY_STATE` を含む `MUTEX_ALL_ACCESS` 要求は中 IL から拒否される(Windows Integrity Mechanism の既定ポリシー) | **受容**。ただし**起動時例外にしてはならない** —— ゲートは `UnauthorizedAccessException` を捕捉し、D4 の `NoResponse` エラーに落とす(§5 の実装要件)。kxEdit を管理者権限で常用する構成は想定外だが、一度でも昇格起動すると通常起動が詰む形は避ける |

### 【Task 5 仕様レビューで判明 2026-09-15】`UiCrashSink` の owner なし MessageBox

★2(モーダルの吸い込み回避)は `GetLastActivePopup` がオーナーの所有ポップアップを
返すことに依存する。kxEdit のモーダル `ShowDialog` は**すべて owner 付き**で、
owner を省略した `MessageBox.Show` も WinForms が `GetActiveWindow()` をオーナーに
代入するため、通常は問題にならない。

**例外が 1 つある**: メインフォームが**最小化されているとき** `GetActiveWindow()` は 0 を返し、
owner なしの `MessageBox` は真に所有者なしで作られる。このときオーナー側からは
どうやっても辿れない(実測: `GetLastActivePopup` も `GW_ENABLEDPOPUP` も救えない)。

該当するのは `src/kxEdit.App/UiCrashSink.cs` の `MainFormCrashHost.ShowMessage` のみ。
クラッシュ通知は `Application.ThreadException` や背景スレッド例外から発火するため、
**最小化中にも出うる**。`MainFormCrashHost` は `MainForm` を保持しているので、
`MessageBox.Show(form, ...)` にするだけで解消する。

**今回は受容**(クラッシュ通知経路のみ・単一インスタンス化のスコープ外)。
将来タスクで回収すること。

### 【Task 2 仕様レビューで判明・受容 2026-09-14】ワイヤ形式は空白区切りのままではパスを運べない

`SingleInstanceRequest` の今日のワイヤ形式は `KXEDIT1 ACTIVATE` ——**半角空白区切りで
ちょうど 2 トークン**である。§6 の想定どおり将来ファイルパスを載せるとき、
この形式のまま `parts[2..]` を空白で再結合する素朴な拡張は**破綻する**:

- Windows のファイルパスは**空白を含みうる**ため、パスが複数になった途端にどこで
  区切れるのかが曖昧になる。
- 先頭・末尾の空白を持つパスは復元できない。

**対応方針(将来タスクで回収)**: パスを載せる時点で、区切りを `\t`
(Windows のファイル名に使えない文字)へ変えるか、`ProtocolTag` を `KXEDIT2` へ上げる。
`ProtocolTag` は非互換変更の逃げ道として既に用意してあるので詰んではいない。

今日は**受容**する —— 今日のペイロードは空であり、先回りして区切りを変えても
検証できる差が無い(YAGNI)。
