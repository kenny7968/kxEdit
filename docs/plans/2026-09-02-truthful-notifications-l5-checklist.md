対象ブランチ: `feature/truthful-notifications`

**このブランチの L5 は必須**(設計書 §9 / 傘設計書 §4.2)。B5 は **App の Speech 系
(`IAnnouncer.Say`)に新しい発声を 3 種類足し、既存 1 種の発声順を変える**変更であり、
CLAUDE.md §5 の「App の Speech 系に触れる変更は必須」に真正面から該当する。

**単独では回さない。** 本チェックリストは傘設計書 `2026-08-31-v0.2-remaining-work-design.md` §7.1 の
「新規」欄に属し、**B1〜B6 完了後にまとめて 1 回**実施する L5 の一部である。

> ## ★★ §4 は `%APPDATA%\kxEdit\` の実ファイルを壊す ★★
>
> kxEdit は**設定ファイルのパスを引数で受け取らない**(`Program.Main` は `SettingsStore.DefaultPath`
> 固定)。したがって**実ファイルを壊す以外に `Unreadable` 起動を作る手段が無い**。

> - **§0.3 の退避を取らずに §4 へ進まないこと。**

> - §4 は `.bak` を作る。**復元時に `.bak` も消すこと**(消さないと次回の検証で「前回の残骸」を

## 0. 準備

### 0.1 なぜ L5 が要るか(自動テストで届かない範囲)

| 事実 | 状況 |
|---|---|
| 発声文言の**中身**・分岐・順序 | L3 で固定済み(`MainFormSmokeTests` / `AnnouncerTests`)。**L5 で確かめ直さない** |
| **実際に SR が読み上げるか**・**どう聞こえるか** | **自動テストでは原理的に検証不能。L5 でのみ確認できる**(CLAUDE.md §2 の a11y 鉄則) |
| 短い発声の直後にモーダルが立ち上がったとき、SR が発声を最後まで読むか | 同上。**M-22 の二段構え(発声 + ダイアログ)の前提そのもの** |
| 発声が**上書きで消えないか**(`AutomationNotificationProcessing.MostRecent`) | 同上。M-8 と I-1(設定 OK 経路)の核心 |

`tools/sr-regression.ps1` は **UIA 応答の検証まで**で、**実発声は検出できないため L5 の代替にならない**
(CLAUDE.md §5)。

### 0.2 環境

- NVDA を起動し、**スピーチビューアー**を開く(PR #53 で確立した逐語検証手法)。
  聞き取りではなくビューアーの**テキストで**照合すること。
- **バックアップ間隔を最短の 5 秒に**する(設定 → バックアップ)。既定は 300 秒で、
  §3 は tick を何度も待つ必要がある。`Math.Clamp(intervalSeconds, 5, 3600)` により 5 秒が下限。
- §3 / §4 の前に**未保存の作業を残さない**。

### 0.3 退避(§4 に入る前に必ず)

```powershell
$d = "$env:APPDATA\kxEdit"
Copy-Item "$d\settings.json" "$d\settings.json.L5BACKUP" -Force
Get-FileHash "$d\settings.json" -Algorithm SHA256   # ← 出力を控える
```

## 1. M-8 — 最後に読まれるのが着地セルであること

**直した欠陥**: 窓外の即時 Raise が armed 済みの trailing を取り消さず、直後に trailing が発火して
**1 つ前のメッセージが最後に読まれる**ことがあった。

**なぜ L5 が要るか**: 発声の**順序**は L3 で固定したが、**キーリピートの実速度が throttle 窓
(50 ms)をまたぐかどうか**は実機でしか分からない。またがなければ現象自体が起きない。

| # | 手順 | 期待 | 判定 |
|---|------|------|------|
| 1-1 | CSV ファイルを開き CSV モードへ入る。→ を**押しっぱなし**にして数セル進め、離す | スピーチビューアーの**最後の行**が、**キャレットが実際に居るセル**を指していること | |
| 1-2 | 1-1 を ↓ でも行う | 同上 | |
| 1-3 | 1-1 を、途中で一瞬止めながら(窓内 Say と窓外 Say を混ぜる)行う | 同上。**1 つ手前のセルが最後に来ないこと** | |

> **修正前の現象を先に観測できると理想的**だが、必須ではない。観測できなかった場合は
> 「**このリピート速度では再現条件に達しなかった**」と記録すること(「直った」と書かない)。

## 2. M-22 — 設定保存の失敗を実態どおりに言うこと

**直した欠陥**: `SaveSettingsSafe` が例外を握るため、保存が落ちても「設定を適用しました」と発声していた。

| # | 手順 | 期待(スピーチビューアーで逐語照合) | 判定 |
|---|------|------|------|
| 2-1 | `settings.json` を読み取り専用にする(`attrib +r`)。設定ダイアログを開き、何か変えて OK | **「設定を適用しましたが、保存できませんでした。この設定は次回起動時に残らない可能性があります」**。「設定を適用しました」で終わらないこと | |
| 2-2 | 2-1 の続き。**ダイアログは出ないこと** | MessageBox が出ない(読み取り専用は通常失敗であり、差替失敗ではない) | |
| 2-3 | 読み取り専用を解除し、もう一度 OK | **「設定を適用しました」**(退行の証人) | |

> **ダイアログ分岐(残留 tmp の案内)は L5 の合否対象から外す。** `AtomicReplaceFailedException` は
> 「差替に失敗し**かつ原本が失われ**かつ復旧リネームも失敗」でしか出ず、**静的なファイル属性の
> 操作だけでは到達しない**(M-22 実装時に確認・`cf17bdb`。条件は `AtomicFile` のクラス
> xmldoc)。「再現不能」ではない —— 別プロセスで
> `settings.json` を高速に削除・再作成し続ければ確率的に到達しうるが、**L5 の手順として安定しない**。
>
> **「短い発声の直後にモーダルが立ち上がったとき NVDA が発声を最後まで読むか」は §3-10 で
> 検証する。** 最終レビュー I-2 で「同時故障では設定保存の失敗をダイアログへ回す」を足した結果、
> **静的なファイル属性の操作だけで発声 → モーダルの並びに到達できるようになった**
> (読み取り専用の `settings.json` + 書込不可のバックアップ先)。M-22 の残留 tmp 案内そのものの
> 文面は依然として本チェックリストでは出せないので、**そこだけは未検証のまま残る**
> ことを申し送りとして記録する(隠さない)。

## 3. M-20 — バックアップ書込の失敗と復旧を、遷移で 1 回だけ言うこと

**直した欠陥**: 書込失敗は `ForceWrite` 再試行だけで握られ、ユーザーに**一度も**知らされなかった。

**準備**: バックアップ間隔を 5 秒にし(§0.2)、未保存の変更があるタブを 1 つ用意する。
バックアップ先(`%APPDATA%\kxEdit\backups\session-*`)を**書込不可**にする方法は、
そのセッションの `session-*` フォルダーに対して自分の書込権を deny するのが確実。

| # | 手順 | 期待 | 判定 |
|---|------|------|------|
| 3-1 | 書込不可にして tick を待つ | **「バックアップを保存できませんでした。未保存の内容は復元できない可能性があるため、ファイルを保存してください」** | |
| 3-2 | さらに 2〜3 tick 待つ | **鳴らない**(遷移でのみ報告する) | |
| 3-3 | 書込可へ戻して tick を待つ | **「バックアップの保存を再開しました」** | |
| 3-4 | さらに 2〜3 tick 待つ | **鳴らない** | |

### 3.1 ★ 3-5 以降の前提 —— 「報告がその pass の中で鳴る」状態を決定的に作る

M-20 は**遷移でしか鳴らない**。したがって設定 OK / 終了フラッシュの**中で**報告を起こすには、
その pass に入る時点で **(a) 健全とみなされている** かつ **(b) 失敗した書込の通知が未 drain で
溜まっている** の両方が要る。drain は `Reconcile` の先頭 1 か所(Timer.Tick / タブ切替 /
設定 OK / 終端フラッシュ)にしかなく、書込の失敗通知は**その pass の drain より後に**背景
スレッドから届くため、報告を出すのは**失敗を作った pass の次の drain**である。

決定的に作る手順(以下「**仕込み**」と呼ぶ):

1. バックアップ間隔を **3600 秒**にして OK(以後 tick が割り込まない)。未保存の変更を持つ
   タブを 2 つ用意する。
2. バックアップ先を**書込可**にしたまま、タブを 2 回切り替える。
   (直前が unhealthy なら、ここで「**バックアップの保存を再開しました**」が鳴る = 想定どおり。)
3. バックアップ先を**書込不可**にし、タブを 1 回切り替える(この pass の書込が失敗する)。
4. この状態で目的の操作(設定 OK / 終了)を行う。

> 間隔 5 秒のままでも同じ状態は作れるが、**次の tick が先に drain すると空振りする**。
> 空振りは 3-6 / 3-9 の期待どおりの結果と**見分けが付かない**ので、必ず上の手順で作ること。
> 仕込み 4 で何も鳴らなかった場合は、手順 2 からやり直す(FAIL と記録しない)。

| # | 手順 | 期待 | 判定 |
|---|------|------|------|
| 3-5 | 仕込みの後、**設定ダイアログを開いて OK** | 最後に残るのが**バックアップの警告**であること(「設定を適用しました」で上書きされない) | |
| 3-6 | 3-5 の直後に**もう一度**設定ダイアログを開いて OK | **「設定を適用しました」**が読まれること(バックアップの警告を**繰り返さない**) | |
| 3-7 | 仕込みをやり直し、**アプリを終了**する | 終了時に**健全性の発声が出ないこと**(助言が実行不能なため抑止している) | |
| 3-8 | 3-7 で終了を**キャンセル**した場合 | キャンセル後に**バックアップの警告が言い直されること** | |
| 3-9 | 3-8 の後、**もう一度**終了して**キャンセル**する | **鳴らないこと**(2 度目は抑止が起きていない) | |
| 3-10 | 仕込みをやり直し、さらに `settings.json` を読み取り専用にしてから**設定 OK** | **ダイアログ**「設定を保存できませんでした」が出て、**閉じた後に**バックアップの警告が読まれること。設定保存の失敗が**どこかで必ず届く**こと | |

> **3-5 は I-1 の実機確認。** 設定ダイアログ OK は内部で `Reconcile` を走らせるため、
> M-20 の失敗発声が M-22 の成功発声に**上書きされる**経路があった。設定 OK の側が
> **発声チャネルを譲る**(この pass で健全性が鳴ったら設定の結果を発声しない)ことで塞いでいる。
>
> **3-6 / 3-9 は「事象ベース」の実機確認**(最終レビュー I-2 / M-7)。譲る・言い直すのは
> **その呼出の中で実際に報告が鳴った(あるいは抑止された)とき**だけで、
> 「今 unhealthy か」では判断しない。状態で判断していると、設定 OK のたび・キャンセルのたびに
> 同じ警告が繰り返し鳴る。
>
> **3-7 / 3-8 は I-2 の実機確認。** 終端では「ファイルを保存してください」が原理的に実行不能で、
> かつ同じ pass の `ForceWrite` 再試行が成功すると発声が偽になる。抑止したが、**キャンセルで
> 編集へ戻ると誰にも伝わらないまま居座る**ので言い直している。
>
> **3-10 は最終レビュー I-2 の中核。** 発声チャネルは 1 行しか載らない(50 ms 窓 +
> `MostRecent`)ので、**同時故障では設定保存の失敗をダイアログへ回す**。これは
> 「通常失敗にダイアログを出さない」(§2 の 2-2)に対する**意図的な例外**なので、
> 2-2 と矛盾しない —— 2-2 はバックアップが健全な場合の手順である。
>
> **一過性の失敗では「失敗」「復旧」が 2 回鳴るのは受容済み**(設計 §5.5 (b))。3-1〜3-4 で
> 余計に鳴っても、それが**遷移のたび 1 回ずつ**なら仕様どおり。

## 4. B4 申し送り — `Unreadable` の退避 ★★ 実ファイルを壊す ★★

**直した問題**: 起動時に「先にコピーしてください」と案内しながら、ユーザーが対処する前に
`OnFormClosing` / `RegisterRecent` が**案内した当のファイルを上書き**していた。

**§0.3 の退避を取っていることを確認してから進むこと。**

### 4.1 DENY-READ ACL 版 —— **`(RD)` で張ること。`(R)` では belt の検証にならない**

Task 5(退避の実装・`8821246`)の実測で確定した事実(正は `SettingsStore.TryQuarantineUnreadable`
の xmldoc):

| deny 指定 | `ReadAllText` | `File.Move`(= 退避) |
|---|---|---|
| **`(RD)`** | 失敗(`Unreadable` になる) | **成功** ← belt が効く |
| `(R)` / `(GR)` | 失敗 | **失敗**(`SYNCHRONIZE` ごと拒否され、改名側も要求するため) |

**`(R)` で張ると「退避できなかった側」の確認になる。**belt を確かめたいなら `(RD)`。

| # | 手順 | 期待 | 判定 |
|---|------|------|------|
| 4-1 | `settings.json` に `(RD)` の deny ACE を張って kxEdit を起動 | 起動時警告が出る。文言に**原本パス**が載り、**`.bak` へ退避を試みる旨**と**「不要になったら削除してください」**が含まれる | |
| 4-2 | 4-1 の文言をスピーチビューアーで逐語照合 | **パスに改行が混ざらない**(無害化が効いている)。**行動指針がパスより前**にあること | |
| 4-3 | 何かファイルを開くか、そのまま終了する | `%APPDATA%\kxEdit\settings.json.bak` が**でき、中身が退避前の設定である**こと | |
| 4-4 | 4-3 の後、もう一度保存が走る操作をする | `.bak` の中身が**書き換わらない**こと(退避は 1 回だけ) | |
| 4-5 | 警告文だけを聞いて `.bak` の在りかを特定できるか | ユーザーが原本パスから導出する必要がある。**できなければ「導出が必要」と記録**(欠陥ではなく構造的な帰結) | |

### 4.2 一過性ロック版 —— **4.1 とは別の失敗モード**

| # | 手順 | 期待 | 判定 |
|---|------|------|------|
| 4-6 | 別プロセスで `settings.json` を**排他で掴んだまま** kxEdit を起動 | 起動時警告が出る | |
| 4-7 | **掴んだまま**、保存が走る操作を 1 回する | 退避も保存も落ちる(観測できなくてよい) | |
| 4-8 | ロックを解放し、もう一度保存が走る操作をする | **`.bak` に「以前の設定」が入っている**こと。原本が `.bak` を残さず消えていないこと | |

> **4.6〜4.8 は Task 5 の I-1 が直した経路。** 修正前は、最初の保存がロック中に来ると belt が
> 使い切られ、ロック解放後の保存で**原本が `.bak` を残さず消えていた**。

## 6. 復元(§4 を実施したら必ず)

```powershell
$d = "$env:APPDATA\kxEdit"
icacls "$d\settings.json" /remove:d "$env:USERNAME"   # 4.1 で張った deny ACE を消す
attrib -r "$d\settings.json"                           # 2-1 の読み取り専用を消す
Remove-Item "$d\settings.json.bak" -ErrorAction SilentlyContinue   # 4.3 / 4.8 の退避を消す
Copy-Item "$d\settings.json.L5BACKUP" "$d\settings.json" -Force
Get-FileHash "$d\settings.json" -Algorithm SHA256      # ← §0.3 の値と一致することを確認
Remove-Item "$d\settings.json.L5BACKUP"
```

**SHA-256 が §0.3 と一致しない場合は復元できていない。** 一致するまで終了しないこと。
§3 で `session-*` に張った deny ACE も戻すこと。
