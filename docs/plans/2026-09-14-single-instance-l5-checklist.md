# L5(実機検証)チェックリスト — 多重起動の禁止(単一インスタンス化)

策定日: 2026-09-15
対象ブランチ: `feature/single-instance`
ベース commit: main `1ad14a4`(PR #76 = v0.2 L5 統合のマージ後)
設計書: `2026-09-14-single-instance-design.md` / 実装計画: 同名(`-design` なし)

**本件の L5 は「実機 SR 検証」と「実機目視」の両方**。2 つ目の起動でウィンドウの
フォアグラウンドが移るため、**SR が何を読み上げるかが変わる**(App の Speech 系や
`kxEdit.Accessibility` のコードには触れていないが、読み上げの起点となるフォーカスが動く)。
CLAUDE.md §5 の判定「迷ったら必要に倒す」に従い**必須**とする。

判定欄には **PASS / FAIL / N/A** を記入し、FAIL は**起きた状態を具体的に**残すこと
(「前面化しない」ではなく「タスクバーのボタンが橙色に点滅するだけでウィンドウは前に出ない」
のように)。

## 0. 準備

### 0.0 時間が限られるときの優先順位

Task 7 仕様レビューの判定により、**次の 3 項目は L3(自動テスト)が原理的に届かず、かつ
今回の変更が新しくリスクを作った箇所**である。時間が取れない場合でもここだけは実施すること。

| 項目 | なぜ最優先か |
|---|---|
| **21**(既存の起動直後に 2 つ目) | `PendingActivation` の保留 → `Attach` 消化は**今回新設した配線で、production 経路を通す自動テストが 1 本も無い**。単体テストは `PendingActivation` を直接叩いているだけで、`form.Shown += pending.Attach(form)` が実際に発火するかは誰も見ていない |
| **22**(高 DPI でのエラーダイアログ) | T-1(`ApplicationConfiguration.Initialize()` をゲートより前へ移した)の**唯一の実地検証点**。移動の是非そのもの |
| **19**(`ForeignPeer` の実文言) | Task 6 のテストは引き渡しを**注入**しているため本番の写像を見ていない。「別の場所にある」と書かれていないことは L3 では確認できない |

### 0.1 ⚠️ 最重要: 2 つ目は「実際のユーザー操作」で起動すること

**スクリプト(PowerShell / バッチ / `Process.Start`)から 2 つ目を起動してはならない。**
動いている機能を FAIL と誤判定する。

理由: Windows は任意プロセスの `SetForegroundWindow` を拒否する。設計上、前面化できるのは
**今まさにユーザーが起動した 2 つ目**の方で、そちらが `AllowSetForegroundWindow(既存の PID)` で
権利を既存インスタンスへ譲渡してから依頼する(設計 §4 ★1)。ところが**スクリプトが起動した
プロセスはユーザー入力を一度も受けていないためフォアグラウンド権を持たず、譲るものが無い**。

**紛らわしいのは、引き渡し自体は成功すること**。2 つ目は終了コード 0 で無言終了し、ウィンドウも
作らない。**「前面化だけしない」**ので、ログや終了コードを見ている限り成功に見え、目視だけが
失敗する。2026-09-15 の Task 7 手動確認で実測済み。

→ 2 つ目の起動は **`Win+R` にパスを入力**、**エクスプローラでダブルクリック**、
**ショートカット / スタートメニュー**のいずれかで行うこと。

### 0.4 自動テストでは届かない範囲(ここを実機で見る)

- **フォアグラウンドが実際に移るか**。`SetForegroundWindow` の成否は OS の状態(フォアグラウンド権・
  UIPI・仮想デスクトップ)に依存し、テストプロセスからは再現できない。
- **SR が何を読み上げるか**。CLAUDE.md の a11y 鉄則どおり、実発声は自動テストでは検証できない。
- **モーダルダイアログの吸い込み**(設計 §4 ★2)。`GetLastActivePopup` の挙動は実ウィンドウが要る。
- **最小化からの復帰が元の状態(通常 / 最大化)を保つか**。
- **エラーダイアログの見え方**(高 DPI でぼやけないか)と**文言の妥当性**。

## 5. 権限・表示環境(degrade の確認)

| # | 手順 | 期待 | 判定 | 所見 |

| 23 | 既存を**管理者として実行** → 通常権限で 2 つ目を起動 | **起動時にクラッシュしない**こと。エラーダイアログが出る(文言は項目 19 と同じ想定。設計 §4 の訂正どおり `ForeignPeer` に落ちる) | | |
| 24 | 逆順: 通常権限で起動 → **管理者として** 2 つ目を起動 | 同上。クラッシュしないこと | | |
| 24b | **別の一般ユーザー**として `runas /user:<別アカウント> kxEdit.exe`(kxEdit を一切起動していない状態で) | **普通に起動すること**。<br>※最終脆弱性レビューの**未再現の仮説**: `\Sessions\N\BaseNamedObjects` の DACL には Everyone の CREATE_OBJECT が無いため、同一セッションに `runas` で入った**非管理者の別ユーザーは自分専用の名前でも Mutex を作れない**可能性がある。そうなると `new Mutex` が `UnauthorizedAccessException` → `NoResponse` → **何も起動していないのに「既に起動していますが応答しません」**が出る。<br>レビュアーは別アカウントが無く再現できなかった。**ここが FAIL なら、その経路を `FirstInstance`(排他せず通常起動)へ倒す修正が要る** —— 「起動できない」より「排他しない」方が害が小さいため。<br>※管理者資格情報での UAC 昇格は `BUILTIN\Administrators` の ACE があるため影響を受けない(= 項目 23/24 とは別の話) | | |
