# L5(実機 SR 検証)チェックリスト — 保存の最終防衛線(M-12 / M-13 / M-11・B4)

対象ブランチ: `feature/save-last-line-of-defense`
設計書: `2026-09-02-save-last-line-of-defense-design.md` / 実装計画: 同名(`-design` なし)

**このブランチの L5 は必須**(設計書 §7 / 傘設計書 §4.2)。M-11 が **SR の読む面(`MessageBox`)を
新設**しており、CLAUDE.md §5 の「App の Speech 系に触れる変更は必須」に直接該当する。

**単独では回さない。** 本チェックリストは傘設計書 `2026-08-31-v0.2-remaining-work-design.md` §7.1 の
「新規」欄に属し、**B1〜B6 完了後にまとめて 1 回**実施する L5 の一部である。重複する操作は §7 に挙げた。

**判定欄は実施前なので空にしてある。** 実施時に **PASS / FAIL / N/A** を記入し、FAIL は
「聞こえた文言」または「見えた状態」を逐語で残す。

> ## ★★ この検証は `%APPDATA%\kxEdit\` の実ファイルを壊す ★★
>
> kxEdit は**設定ファイルのパスを引数で受け取らない**(`Program.Main` は `SettingsStore.DefaultPath`
> 固定 = `%APPDATA%\kxEdit\settings.json`)。したがって**実ファイルを壊す以外に破損起動を作る手段が無い**。
>
> - **§2.1 の退避を取らずに §3 へ進まないこと。**
> - **終わったら §5 の復元を必ず実行すること**(SHA-256 の一致まで確認する)。
> - 検証中は kxEdit の**通常作業をしない**。最近使ったファイルの一覧・ウィンドウサイズ・
>   セッションレイアウトも書き換わる。

### 0.3 ★ 弁別できない観測を、できるふりで書かない

PR #62 の最終レビュー Critical-1(修正前でも全行 PASS するチェックリスト)を踏まないため、

本書で**弁別できないもの**は次の 3 つで、いずれも項目本文に明記してある。

| 観測 | なぜ弁別できないか | どう扱うか |
|---|---|---|
| 「`%APPDATA%` 配下のパスが 1 行で読まれる」(`OneLine` の畳み込み) | 実パス `%APPDATA%\kxEdit\settings.json.bad` には**畳み込む対象が 1 つも無い**(連続空白も制御文字も無い)ので `OneLine(path) == path`。**恒真**である(L3 が `AssertSanitizationIsObservable` で潰した罠と同型・§10.19 指摘 B) | **`OneLine` の網ではない**と明記したうえで、「NVDA が長いパスを途中で切らずに読むか」という**読まれ方**の観測として残す |

| 「大きい文書の Ctrl+S で待たされない」(項目 8) | 修正前後を実機で A/B できない(ビルドを差し替えるしかない) | **弁別項目ではない**と明記し、§10.10 の実測値を判断材料として併記する |

## 1. 実施のノウハウと、この検証固有の罠

### 1.0 ⚠ 起動 1 回ごとに settings.json は書き直される —— fixture は項目ごとに植え直す

kxEdit は**ユーザーが設定を 1 つも変えなくても** settings.json を書き直す。

| 上書きの契機 | 実物(HEAD 時点) |
|---|---|
| 終了するたび | `MainForm.cs:665` の `SaveSettingsSafe()`(`OnFormClosing` 内) |
| ファイルを開く / 切り替える / 保存するたび | `FileController.cs:1571-1575` の `RegisterRecent` → `_saveSettings()` |

したがって **1 回起動して終了した時点で、壊した settings.json は既定値の正常なファイルへ戻っている。**
同じ fixture を次の項目へ使い回すと `Ok` 判定になり、**その項目は何も検証しない**(CSV F2 の
チェックリスト §1.2 と同じ罠)。**項目ごとに §2.4 のコマンドで植え直すこと。**

これは本ブランチの文言が「設定を変更すると上書きされます」ではなく
「**kxEdit はファイルを開いたときや終了するときに設定を書き直すので**」になっている理由そのもの
(§10.15 (1))で、**検証手順の側でも同じ事実を踏む。**

### 1.1 ⚠ 起動前に kxEdit が動いていないこと

fixture を植える前に必ず確認する。動いたまま植えると、そのプロセスの終了時保存が上書きする。

```powershell
Get-Process kxEdit -ErrorAction SilentlyContinue   # 何も出ないこと
```

### 1.2 ⚠ Windows PowerShell 5.1 の罠(手順のコマンドはこれを踏まないように書いてある)

- **`[IO.File]::Move` に 3 引数(overwrite)版は無い。** PowerShell 5.1 は .NET Framework 上で動くため、
  `Move($src, $dst, $true)` は `MethodException` になる(実測)。本書は 2 引数版か `Move-Item -Force` を使う。
  **アプリ側(.NET 9)は 3 引数版を使っている** —— 同じ API に見えて別物なので、
  「PowerShell で再現できた/できない」をアプリの挙動の根拠にしないこと。
- **fixture の中身に日本語を入れない。** コンソールへ貼る文字列は CP932 で読まれうる
  (メモリー `bash-heredoc-mangling-on-windows`)。破損内容は表示されないので **ASCII で十分**。
  本書の fixture は `not a json { broken settings for L5` に統一してある。
- ログをファイルへ出すときは `Out-File -Encoding utf8` を明示する(CLAUDE.md §10)。

### 1.3 発声の逐語確認をどこで使うか

| 項目 | 逐語(スピーチビューアー) | 聞いて判断 / 目視 |
|---|---|---|
| 1 / 2 / 3 / 4 | **必須**(文言・語順・タイトルが観測面そのもの) | フォーカス位置と閉じた後の戻り先は目視 + 操作 |
| 5(順序) | **必須**(2 つの警告の**並び順**をログで確定する) | — |
| 6(初回起動) | あってよい(**ログに何も出ないこと**の補強) | 主判定は「ダイアログが出ない」の目視 |
| 7(設定維持) | 不要(「設定を適用しました」が読まれることだけ観測) | 主判定は目視とファイル |
| 8(保存の体感) | 不要 | 体感のみ |

- windows-mcp の `Snapshot` は `use_ui_tree=true` で応答が返らないことがある。
  **`use_ui_tree=false` + スクリーンショットの座標読み**で完走できる。
- **ステータスバーの発声ラベルは `IAnnouncer` が読む文字列そのもの**だが、
  **`MessageBox` は `IAnnouncer` を通らない**(`MainForm.ShowSettingsStartupWarning` は
  `MessageBox.Show` を直に呼ぶ)。**本書の項目 1〜5 でステータスバーは観測面にならない。**
  スピーチビューアーが使えないなら、**画面の文言を逐語で書き写して「発声は未検証」と明記する**
  (PR #57 の第 1 回と同じ書き分け)。

## 2. 事前準備

### 2.1 ★必須 —— `%APPDATA%\kxEdit\` をまるごと退避する

```powershell
Get-Process kxEdit -ErrorAction SilentlyContinue        # 起動していないこと

$src = Join-Path $env:APPDATA 'kxEdit'
$bak = Join-Path $env:USERPROFILE 'kxEdit-l5-backup'
if (Test-Path $bak) { throw "退避先が既にある。前回の L5 が §5 で復元されていない可能性がある" }
Copy-Item $src $bak -Recurse -Force

# 復元の検算用。この値を §8 の実施記録へ控える。
(Get-FileHash (Join-Path $bak 'settings.json') -Algorithm SHA256).Hash
```

`%APPDATA%\kxEdit` がまだ無い環境(kxEdit を一度も起動していない)なら退避は不要だが、
**その場合は §5 で `%APPDATA%\kxEdit` を丸ごと削除して初期状態へ戻す**と §8 に書いておくこと。

### 2.2 ビルドと起動

```powershell
dotnet build kxEdit.sln -c Release
$exe = "<リポジトリ>\src\kxEdit.App\bin\Release\net9.0-windows\kxEdit.exe"
```

項目 4(多重起動)以外は `dotnet run --project src/kxEdit.App -c Release` でもよい。
**項目 4 だけは `Start-Process $exe` を 2 回続けて撃つ必要がある**(`dotnet run` はビルド判定が
入って起動タイミングが揃わない)。

### 2.3 NVDA

1. NVDA を起動し、**スピーチビューアー**(NVDA メニュー → ツール → スピーチビューアー)を開く。
   PR #57 の第 1 回では windows-mcp から NVDA メニューを操作できなかった。
   **開けない場合はユーザーに開いてもらってから開始する。**
2. 項目ごとにログをクリアするか、開始時刻を控えて区切りを付ける。

### 2.4 fixture を作る 4 つの道具(項目本文から参照する)

```powershell
$p = Join-Path $env:APPDATA 'kxEdit\settings.json'

# (A) 壊す(Corrupt にする)。ASCII のみ(§1.2)。
function Set-CorruptSettings {
    [IO.File]::WriteAllText($p, 'not a json { broken settings for L5', [Text.UTF8Encoding]::new($false))
}

# (B) 前回の退避先を消す(「.bad が生えた/生えない」を観測面にするため毎回消す)。
#     ディレクトリ版((C) の後始末)も消せるよう -Recurse を付ける。
function Clear-Bad { Remove-Item "$p.bad" -Recurse -Force -ErrorAction SilentlyContinue }

# (C) 退避を確実に失敗させる(宛先をディレクトリにする)。
#     File.Move は宛先がディレクトリなら overwrite:true でも失敗する
#     —— L3 の Prepare_does_not_point_at_a_quarantine_that_was_never_created が同じ形。
function Block-Quarantine { New-Item -ItemType Directory -Path "$p.bad" | Out-Null }

# (D) 読めなくする(Unreadable)。★ロックは FileShare.Delete。
#     読み取りだけを拒否し、改名は許す。FileShare.None にすると
#     「退避を呼ばないこと」ではなく「呼んでも失敗すること」しか見えない(§10.15 の fixture 欠陥と同型)。
#     このコンソールは開いたままにする。解放は $fs.Dispose()。
$fs = [IO.File]::Open($p, [IO.FileMode]::Open, [IO.FileAccess]::Read, [IO.FileShare]::Delete)
```

> **(D) の性質はこの機で実測済み**(2026-09-02): `FileShare.Delete` のロック中、
> `[IO.File]::ReadAllText` は `IOException`(共有違反)、`[IO.File]::Move` は**成功**する。
> = アプリが誤って `Unreadable` でも退避したなら、**`.bad` は実際に生える**。
> だから「`.bad` が生えない」が観測になる。

## 4. 判定

> **ブロックする対象はマージではなくリリースである。** 本書の L5 は傘設計書 §7 のとおり
> **B1〜B6 のマージ後にまとめて 1 回**回す。FAIL は「リリース前に直す」= 修正 → 再実施 の対象になる。

- **項目 1 が FAIL なら M-11 の通知は届いていない。リリースしない。**
  タイトルとアイコンは**自動テストが 1 ビットも守っていない**(§10.19 の変異が生存)ので、
  ここが唯一の確認点である。
- **項目 2 / 3 が FAIL なら文言の枝が壊れている。** どちらも「上書きされる前にコピーしてください」を
  伝える枝で、**壊れると案内どおりに行動できない**。
- **項目 5 の順序が逆なら FAIL**(設定が既定へ戻った事実は、復元の見え方が変わった理由でもある。
  §10.18 の表示位置の判断)。
- **項目 6 が FAIL(初回起動で警告が出る)なら退行。リリースしない。** 全ユーザーが毎回踏むので M-11 より痛い。
- **項目 7 の観測 B が取れなければ「未検証」と書く。** 観測 A(維持)だけを見て PASS にしない
  —— **修正前でも PASS する**。
- **項目 4 は `N/A(未再現)` を許す。** 10 回試して踏めなかったことを記録する。
- **項目 8 は弁別ではない。** PASS は「退行が見えなかった」以上の意味を持たない。そう書く。
- 各項目とも、**fixture を植え直さずに連続実施した回は判定しない**(§1.0)。
  2 回目以降の起動では設定が既定値の正常ファイルへ戻っているため、**何も検証していない**。

| **M-12 の復旧経路**(差替の部分失敗で tmp を残す / `File.Move` で復旧する) | **実機で `File.Replace` の部分失敗を決定的に起こせない**(設計 §7 / §6.1)。起こせない以上、「起こらなかった」と「直っている」を区別できず、**何を観測しても修正前でも同じ結果になる**。担保は `AtomicFile` の差替段 seam に注入する L1 の 5 分岐 |
| **M-12 の文言**(「書き込んだ内容は `<退避先>` に残してあります」/ 残せなかった側) | 上と同じ理由(§10.6 の「L5」節が同じ判断を明記)。**SR 前提の文言設計はしているが、実発声は未確認**という状態のまま残る。踏める配線ができたら項目へ昇格させること |
| **M-13 の fsync が実際にディスクへ届いたこと** | 電源を落とせない。届いたことは原理的に観測できず、`Flush(true)` を `Flush()` へ退化させる変異を殺すモック検証しかできない(設計 §6.2)。項目 8 で見るのは**副作用(体感)だけ** |
| **`AtomicFile` の `CreateNew`** | ステージング段に観測面が無く、**production へ seam を足さない限り原理的に不可能**(§10.10 指摘 5 の閉じた論証)。実機でも同じ。<br>**※ `FileShare.None` は当初この行に併記していたが誤り** —— L1 で網が張れた(`Staging_handle_denies_a_concurrent_open`・設計 §10.21)。閉じた論証は `CreateNew` にしか当たらない |
| **`Unreadable` のまま終了すると案内した当のファイルが上書きされる** | 挙動としては再現できるが、**本ブランチの判断は「止めない」**(設計 §5.5)。B5(M-22)の検討事項として申し送り済みで、B4 の合否ではない |
| **`{"FontSize":1e400}` で `FontSize = +∞` になる既存バグ** | `Normalize` は本ブランチで無変更 = 既存バグ(設計 §9)。B4 の射程外なので L5 でも見ない |
