## 0. なぜ L5 が必要か(自動テストで届く範囲/届かない範囲)

### 0.1 自動テストで既に固定されている事実(L5 で確かめ直さない)

| 事実 | 網 |
|---|---|
| 観測値(`LastKnownWriteTimeUtc`)を開く前・保存後・復元時に取ること | L3 `FileControllerExternalChangeTests`(観測値の捕捉) |
| 3 文言の**中身**(名前が先頭・問いが末尾・無害化)と、未保存あり/なしで既定側(`defaultNo`)が変わること | L3 `FileControllerExternalChangeTests`(`FakePrompt.YesNoCalls` の `DefaultNo` / `OkCancelCalls` の `DefaultCancel`) |
| 「いいえ」が観測値を動かさず `AcknowledgedWriteTimeUtc` だけ憶える = 次の変更まで聞かず、保存直前の確認は生きたまま | 同上(`Kept` の後の `NoChange` / `SaveDocument` の `OkCancel`) |
| 読み直しが現在の文字コードで固定され(自動判定に戻らない)、キャレット文字位置を戻し、`_openedFresh` を 1 回呼ぶこと | 同上 |
| 再入ガード(モーダルの中で届いた 2 枚目の検知が `Skipped`) | 同上(`FakePrompt.OnYesNo`) |
| 到達不能ルートの 60 秒 TTL・不在と到達不能の区別 | L3 `FileTimestampProviderTests` |
| MainForm が `Reloaded` のときだけ `読み直しました` を言い、手動 CSV モードを `TryEnterMode` で戻してセル位置を (row, col) で戻すこと(自動モードでも戻す・セルが無くなれば先頭セルのまま)、解析不能なら通常モードのまま最後の発声が `CSVとして解析できません` になること | L3 `MainFormExternalChangeTests`(seam 経由) |

> **本数は網の増減で変わる。引用するときは数え直すこと。**

### 0.2 L5 でしか確かめられない事実(本チェックリストの存在理由)

| 未確認 | なぜ自動テストで届かないか |
|---|---|
| **`OnActivated` / `ActiveDocumentChanged` から検知が実際に起動すること** | どちらも `BeginInvoke` 先で `ActiveForm == this` を要求する。L3 の STA ハーネスは実際のウィンドウ活性化を起こせず、`MainFormExternalChangeTests` は seam(`CheckExternalChangeOnActiveForTest`)で本体だけを叩いている |
| **既定ボタンの側**(未保存なし = はい / 未保存あり = いいえ / 保存直前 = キャンセル) | `MessageBoxUserPrompt` の `defaultNo` / `defaultCancel` → `MessageBoxDefaultButton.Button2` の写像は `MessageBox` が blocking で L3 から押せない。**Enter で何が起きるかは実機だけが見ている** |
| **NVDA が実際に何と読むか**(タイトル → 本文 → フォーカスされたボタンの順・語順・ファイル名の読まれ方) | L3 は組み立て済み文字列を `FakePrompt.Log` で見るだけ。UIA 経由の発話は別問題(CLAUDE.md §2) |
| **タブ切替で、ダイアログがタブ名の発声(同期)より後に出ること** | `BeginInvoke` 先が走るにはメッセージポンプが要る |
| **`ReloadFailed`(ロック)でエラーの後に同じ確認が再び出て、「いいえ」で止まること** | エラーダイアログを閉じた直後の `OnActivated` 再発火に依存する(設計 §3.5-2) |
| **CSV モードのタブを読み直した後のフォーカス位置と、NVDA が最後に読むのがセルであること** | `OnActivated` の再発火(フォーカス復帰)は実機でしか起きない。発声は `UiaAnnouncer` の 50 ms 窓で間引かれる(同期に連続する 3 件の `Say` は 1 件目と最後だけが SR に届く)ので、L3 の通知ラベル(最後の 1 件)では NVDA が何を読むかは分からない |
| **OneDrive の同期クライアントが mtime を触らないこと**(誤検知) | 実クライアントの挙動。設計 §5 の「観測」項目 |
| **到達不能な共有で UI が最大 5 秒しか止まらず、60 秒以内の往復は待たないこと** | 実 SMB のタイムアウト挙動。L3 はフェイクの clock と probe |

**実発声は NVDA スピーチビューアーで逐語確認する**(手法は PR #53 で確立)。
「ダイアログが出た」ではなく「**何と読み上げたか**」を記録すること。

PR #62 の最終レビュー Critical-1(修正前でも全行 PASS するチェックリスト)を踏まないため、**各項目に

## 1. 実施のノウハウと、この検証固有の罠

### 1.1 ⚠ 「外部変更」は mtime が動いてはじめて変更になる

比較は**完全一致**(設計 §3.3)。`Add-Content` / メモ帳の保存は NTFS では必ず mtime を進めるが、
**同じクロックティック内の 2 回目の書換は同値になりうる**(設計 §9 の受容事項)。本書の道具
`Set-External`(§2.3)は書いた後に **mtime が前と違うことを検算して**から返る。検算に落ちたら
1 秒待って書き直す(FAT/exFAT のドライブでは 2 秒粒度なので使わない)。

### 1.2 ⚠ 「他のアプリ」は PowerShell コンソールでよい

弁別に要るのは「kxEdit の外で書かれた」ことだけで、メモ帳は要らない。**Alt+Tab の相手を
コンソールに固定する**と、戻り先の取り違えが減る(3 つ以上のウィンドウがあると Alt+Tab は直前の
1 つにしか戻らない)。メモ帳で書く場合は、メモ帳側が**ファイルを掴んだままにしない**こと
(掴んだままなら項目 6 の形になり、読み直しがエラーに落ちる。ロックを作りたいのは項目 6 だけ)。

### 1.3 ⚠ kxEdit を `dotnet run` で起動しない

`dotnet run` のコンソールが Alt+Tab の候補に混ざる。`Start-Process $exe` で起動する(§2.1)。

### 1.4 ⚠ ダイアログを閉じると `OnActivated` が再び来る

確認ダイアログ(`MessageBox`)を閉じると kxEdit が再活性化し、同じ検知がもう 1 度走る。
`Reloaded` / `Kept` なら観測値が更新済みで `NoChange`(黙る)。**同じ確認が 2 回続けて出たら FAIL**
——ただし**項目 6(`ReloadFailed`)だけは意図的に 2 回出る**。混同しないこと。

### 1.5 発声の逐語確認をどこで使うか

| 項目 | 逐語(スピーチビューアー) | 聞いて判断 / 目視 |
|---|---|---|
| 1 / 2 / 3 / 4 / 6 | **必須**(タイトル・本文・フォーカスされたボタン名が観測面そのもの) | 閉じた後の戻り先は目視 + 操作 |
| 5 | **必須**(`読み直しました` → セル、の 2 件が届き**最後がセル**であること。間の `CSVモード オン …` は 50 ms 窓で間引かれる) | セル位置・キャレット行はステータスバー目視 |
| 7 / 8 | あってよい(**ログに `ファイルの変更` が現れない**ことの補強) | 主判定は「ダイアログが出ない」「止まる秒数」 |
| 9 | 不要(`読み直しました` だけ) | 主判定はステータスバーの文字コード表示 |

- **`MessageBox` は `IAnnouncer` を通らない**ので、通知ラベル(ステータスバー最下段)はダイアログの
  観測面にならない。`読み直しました` と CSV の発声は通る(通知ラベルにも出る)。
- スピーチビューアーが使えないなら、**画面の文言を逐語で書き写して「発声は未検証」と明記する**
  (PR #57 の第 1 回と同じ書き分け)。

### 2.3 道具(項目本文から参照する)

```powershell
# (A) 外部変更。mtime が実際に進んだことを検算してから返る(§1.1)。
function Set-External([string]$path, [string]$line) {
    $before = [IO.File]::GetLastWriteTimeUtc($path)
    Add-Content -Path $path -Value $line -Encoding Ascii
    $after = [IO.File]::GetLastWriteTimeUtc($path)
    if ($after -eq $before) { throw "mtime が進んでいない。1 秒待って撃ち直す" }
    "mtime: $($before.ToString('o')) -> $($after.ToString('o'))"
}

# (B) 排他ロック(項目 6)。読み取りも拒否する = kxEdit の読み直しが IOException で落ちる。
#     解放は $fs.Dispose()。このコンソールは閉じない。
function Lock-File([string]$path) {
    [IO.File]::Open($path, [IO.FileMode]::Open, [IO.FileAccess]::ReadWrite, [IO.FileShare]::None)
}
```

> **(B) の性質**: `FileShare.None` のロック中でも `File.Exists` と `File.GetLastWriteTimeUtc` は
> **成功する**(属性の読み取りに共有アクセスは要らない)。だから検知は起き、読み直し(本文の読み取り)だけが
> 失敗する = `ReloadFailed` の経路そのもの。

### 2.4 NVDA

2. 項目ごとにログをクリアするか、開始時刻を控えて区切りを付ける。

### 2.5 設定

### 項目 8 — 到達不能な共有の文書を開いたまま Alt+Tab → 1 回目は最大 5 秒、直後の往復は待たない(60 秒 TTL)

**この修正が無ければどう見えるか**: 復帰時に I/O を**しない**ので、**一切止まらない**。
= 「1 回目に最大 5 秒止まる」は修正**で増えた**コストであり、設計 §3.8 が受容したトレードオフ。
本項目は「止まる」を確かめるのではなく、**止まり方が上限(5 秒)と回数(60 秒に 1 回)に収まること**を見る。

**前提**: 開いた後に到達不能にできる共有(別 PC / VM の共有)。**レジストリのネットワークマッピング等で
偽装しない**(メモリー `subagent-side-effect-guardrails`: 実際に環境を壊した前例)。無ければ **`N/A(環境なし)`**。
`\\192.0.2.1\x` のような最初から到達不能なパスは**開けない**ので本項目には使えない。

| # | 手順 |
|---|---|
| 1 | 共有上の `\\<host>\share\l5.txt` を kxEdit で開く(到達可能な状態で) |
| 2 | 共有側を止める(VM を一時停止 / 共有を無効化 / ケーブルを抜く) |
| 3 | Alt+Tab でコンソールへ → Alt+Tab で戻る。**戻ってから入力が効くまでの秒数**を測る(ストップウォッチ) |
| 4 | **10 秒以内**にもう 1 度往復 → 秒数 |
| 5 | **70 秒以上**空けて往復 → 秒数 |
| 6 | 共有側を戻す → 往復 → 聞かれないこと(mtime は不変) |

| 観測面 | 期待 | 判定 |
|---|---|---|
| 1 回目(手順 3)★ | **最大 5 秒**で戻る(`ProbeTimeout`)。**それを超えて止まったら FAIL**(60 秒の SMB タイムアウトを踏んでいる) | |
| 直後(手順 4)★ | **待たない**(到達不能ルートを 60 秒憶えている = プローブしない) | |
| TTL 後(手順 5) | 再び**最大 5 秒**(記憶が切れて再プローブ) | |

| 復旧(手順 6) | 聞かれない。以後の往復も待たない | |

**TTL が効くのは復帰・タブ切替の検知だけ**(`FileTimestampProvider.GetLastWriteTimeUtc`)。開く・保存・
保存直前の確認は基準を捕捉する経路なので、記憶を素通りして**毎回プローブする**(`ProbeLastWriteTimeUtc`。
最終脆弱性レビュー V-1: 記憶を使うと、共有が落ちて記憶 → 復旧 → 60 秒以内に開く/保存、で基準が null になり
その文書の検知が黙って止まる)。したがって、落ちた共有の文書へ **Ctrl+S すると最大 10 秒**(保存直前の確認

手順 3〜5 の秒数は **Alt+Tab の往復だけ**で測り、Ctrl+S や「開く」を混ぜない(混ぜると 5 秒/10 秒が

> 読み替えると修正前でも PASS するので、**手順 3 の実測秒数を必ず数値で書く**(0 秒なら検知が
> 走っていない = 別の問題)。

## 4. 判定

> **ブロックする対象はリリースである。** FAIL は「リリース前に直す」= 修正 → 再実施 の対象になる。

- **項目 1 が FAIL なら M-18 は届いていない。リリースしない。**

- **項目 4 の順序が逆(ダイアログがタブ名より先)なら FAIL**(設計 §3.4「選択変更ハンドラの中で
  モーダルを出さない」の実機側)。
- **項目 5 でモードが落ちる / 1 行 1 列に落ちる / 通常タブが 1 行目に飛ぶなら FAIL**(退行ではなく実装の欠け)。

- **項目 7 は弁別項目ではない。** PASS は「誤検知が見えなかった」以上の意味を持たない。そう書く。
- **項目 8 は実測秒数を書く。** 「止まらなかった」は PASS ではない(検知が走っていない疑い)。
- **項目 7 / 8 は環境が無ければ `N/A(環境なし)`。PASS にしない。**

|---|---|
| **削除の通知**(ディスクから消えたとき) | 設計 §9 で「何も言わない」と決めた(null → 判定しない)。観測すべき挙動が「何も起きない」で、修正前と区別できない |
| **mtime が同一値のまま内容が変わる書換** | 設計 §5 / §9 の受容事項。NTFS では同一ティック内の 2 回書きが要り、実機で決定的に作れない |
| **保存後の観測窓 / 保存直前の TOCTOU** | 原理的に閉じない(設計 §9)。「起こらなかった」と「直っている」を区別できない |
| **定期ポーリング / `FileSystemWatcher`** | 採らなかった案(設計 §5)。前面のまま変更されたケースは項目 3 の保存直前の確認が受ける |
| **F2 編集中の検知** | 起こらない(ウィンドウを離れた時点で `OnLostFocus → CancelEdit`、タブ切替は `BeforeActiveChange → AbortEdit`)。観測すべき挙動が「起きない」で、確かめるには F2 編集中に外部変更を作る手段が要るが、離れた時点で編集が終わる |
| **再入ガード**(モーダルの中で届く 2 枚目) | L3 `FakePrompt.OnYesNo` で固定済み。実機で 2 枚目を届かせるにはダイアログが開いている間にタブ切替の `BeginInvoke` を積む必要があり、モーダル中はタブ列に触れない |
