## 1. F-4 — 復元された空の無題タブが入力を受け付けない

### 1.1 事実(実測)

- 強制終了前に**空だった**無題タブは、セッション復元後に**文字入力・貼り付け・Enter がすべて no-op**。
  ステータスバーは `行 1, 桁 1` のまま、タブラベルに `*` も付かない。
- **NVDA は打鍵を読み上げる**(Space を押すと `スペース`)。= 入力できたと誤認する。
- 同じセッションで、中身のあった無題タブ・復元されたファイルタブ・その場の `Ctrl+N` は
  **すべて正常に入力できる**。空の無題タブだけが壊れる。

### 1.2 根因(コードで確定)

`FileController.RestoreUntitledFrame`(`src/kxEdit.App/FileController.cs:1591`)は
`_docs.CreateNew()` で文書を作ったあと、**エディタに本文ソースを 1 度も与えない**。

| 復元経路 | ソース投入 |
|---|---|
| `RestoreDirtyFromBackup` | `SetOrReplaceSource(TextBuffer.FromString(...))` あり |
| `RestoreUntitledFromBackup` | あり |
| **`RestoreUntitledFrame`** | **無い** |
| `NewFile()`(Ctrl+N) | `doc.Editor.Text = string.Empty;` あり |

`EditorControl` の書込系はすべて `if (_buffer is null || ReadOnly) return;` で始まる
(`EditorControl.cs:1191` / `:1292` / `:1441` / `:1689` / `:1804` / `:1936` / `:1975` ほか)。
`_buffer` が null のままなので、**編集は例外も発声も出さずに落ちる**。
末尾コメントの「fresh バッファ=Modified=false・本文なし」は、
**バッファがある前提で書かれているが実際には無い**。

### 1.3 直し方

`RestoreUntitledFrame` を `NewFile()` と同じ形に揃える。追加するのは 4 行:

```csharp
doc.Editor.Text = string.Empty;   // ← これが無かった(_buffer が null のままだった)
ApplyEol(doc);
doc.Editor.EmptyUndoBuffer();
doc.Editor.SetSavePoint();        // 空タブは clean = Modified=false(既存の意図どおり)
```

- `SetSavePoint()` を選ぶ(`ClearSavePoint()` ではない)。この経路は
  **`BackupId=null` = 終了時に空だったタブ**の枠を戻すもので、復元すべき編集内容が無い。
  `*` を付けると「保存すべき中身がある」と嘘をつくことになる。
- `ApplyEol` は `doc.State.LineEnding` を `Editor.EolMode` へ移す既存ヘルパ。
  ソース投入後に呼ぶ(他の 2 経路と同順)。

### 1.4 網(L1/L2/L3 で何を固定するか)

`kxEdit.App.Tests` に次を足す(既存の復元系テストと同じハーネス):

1. `RestoreUntitledFrame` 経由で復元した無題タブで **`Editor.Text` への書込が実際に反映される**
   こと。**「バッファが null でない」ではなく「1 文字入れたら本文が変わる」で固定する**
   (null チェックだけだと、将来 `_buffer` の持ち方が変わったときに空虚に緑になる)。
2. 復元直後の `Modified` が false であること(`*` が付かない = 既存の意図の固定)。
3. `LineEnding` がレコードの値で復元されること(`ApplyEol` の追加で壊していないこと)。

> **ミューテーション検証は行わない**(CLAUDE.md §4-A: ファイル I/O とセッション復元は禁止領域)。

## 2. F-1 — 折り返し OFF で長大行が一切描画されない

### 2.1 事実(実測)

折り返し OFF で、1 論理行が一定の長さを超えると**本文が一切描かれない**(真っ白)。
ステータスバーの行/桁・キャレット移動・NVDA の読み上げ・検索は**すべて正常に動く**ので、
**SR 経路だけを見ていると気付けない**。折り返しを ON にすると描画される。

**閾値は文字数で決まり、ピクセル幅では決まらない**(2026-09-14 実測):

| 行の内容 | 文字数 | 概算ピクセル幅 | 描画 |
|---|---|---|---|
| 全角 20,000 | 20,001 | 約 320,000 px | される |
| 半角 40,000 | 40,001 | 約 320,000 px | される |
| **全角 24,000** | 24,001 | **約 384,000 px** | **される** |
| **半角 44,000** | 44,001 | 約 352,000 px | **されない** |

境界の二分:

| 文字数 | 描画 |
|---|---|
| 43,001 / 43,601 / **43,671** | される |
| **43,681** / 43,691 / 43,701 / 44,001 | されない |

`1.5 × 文字数 + 16 ≤ 65535`(Uniscribe が 1 回の `ScriptShape` で確保するグリフバッファの
見積もりと 16 bit のグリフ数上限)を解くと **`n ≤ 43,679`**。実測の境界(43,671 OK /
43,681 NG)と一致する。

### 2.2 根因

`FrameBuilder`(`src/kxEdit.Core/Layout/FrameBuilder.cs:180`)は視覚行のテキストを
`snapshot.GetText(row.SegmentStartChar, row.SegmentLength)` で**丸ごと**取り、
`PaintOp(DrawText, Text: text)` を **1 つ**出す。
折り返し OFF では視覚行 = 論理行なので、`EditorControl.Paint.cs:121` の
`TextRenderer.DrawText` に**論理行全体が 1 回で**渡る。
GDI は上限を超えたときエラーを返さず**何も描かない**ので、症状は「真っ白」になる。

### 2.3 案の比較

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A(採用)** | `FrameBuilder` が長い行を**複数の `DrawText` op へ分割**して出す | PaintOp の列が変わるのは**閾値を超えた行だけ**=既存テストは無改変。Core 側なので単体テストで固定できる | 毎フレーム行長ぶんの計測が残る(既存の性能課題はそのまま) |
| B | 水平スクロール窓を `FrameBuilder` へ渡し、**可視範囲だけ**を出す | 描画も性能も直る | PaintOp の列が**全行で**変わる。`_lastFrame` に依存する UIA 座標 API も巻き込む。v0.2 の射程を超える |

**A を採る。** B は「長大行の描画コスト」(`2026-08-02-large-line-resilience-design.md` の
申し送り)と同じ土俵なので、そちらの続きとして別ブランチで扱う。

### 2.4 直し方(案 A の具体)

`FrameBuilder` に「1 op に載せる最大文字数」を定数で持ち、本文 op の発行を
**その長さで割って複数 op にする**。既存の `EmitBodyTextWithSelection`
(選択境界で最大 3 分割する)と**同じ形**にする。

```
private const int MaxCharsPerTextOp = 16384;
```

- 上限 43,679 に対して **1/2.6 の余裕**を取る。理由は 2 つ:
  - 見積もり式 `1.5n+16` は Uniscribe の実装詳細で、**将来変わりうる**。実測値ぎりぎりに寄せない。
  - 結合文字が多い文字列ではグリフ数が文字数を上回りうる(1 文字 1 グリフとは限らない)。
- 一方で小さくしすぎない。分割は**継ぎ目のたびに計測が 1 回増える**ので、
  通常の行(数百文字)では**絶対に分割されない**大きさにする。

**位置の出し方(ここが設計の芯)**: 各チャンクの X は
**「そのチャンクまでの累積幅」**で出す。`PixelMapper.OffsetToPx`(行頭からの prefix 計測)を
チャンクごとに呼ぶと **O(行長 × チャンク数)** になり、500K 文字の行で毎フレーム数百万文字を
測ることになる(`2026-08-02` が潰した経路の再導入)。
チャンクを 1 回ずつ測って足すと **合計は今と同じ「行あたり 1 回ぶん」**に収まる。

- 分割位置は `TextBoundary.SnapToCodePointStart` で**コードポイント境界へ前方スナップ**する
  (サロゲートペアを割らない。既存の分割と同じ規約)。
- `ICharMetrics.MeasureRun` は非 ASCII を含む run の一括計測が**加算的でない**ため、
  継ぎ目で数 px のずれが出うる。**これは受容する**:
  - ずれるのは **16,384 文字を超える行だけ**。通常の文書では 1 度も起きない。
  - 選択矩形(工程 3)との整合が要るのは選択がある行だが、
    そこは `EmitBodyTextWithSelection` が `OffsetToPx` で位置を出す既存経路を通る
    (§2.5 のとおり、分割はその**内側**で行う)。
  - **「数 px ずれる」と「1 文字も描かれない」なら後者の方が重い。**

### 2.5 選択がある行の扱い

`style.SelectionFore` 指定時は `EmitBodyTextWithSelection` が prefix / 選択内 / suffix の
最大 3 run を出す。**その各 run に対して同じ分割を適用する**(run の X は既存どおり
`OffsetToPx` で出し、run の**内側**を長さで割る)。
= 選択の色分けと分割が二重に効く形にはならない。

### 2.6 何を固定するか(網)

`kxEdit.Core.Tests` の `FrameBuilder` 系に足す:

1. **閾値以下の行では op 数が 1 のまま**であること(既存挙動の不変。分割が漏れ出さない)。
2. 閾値を超える行で **op が複数になり、Text を連結すると元の行と一致する**こと
   (= 1 文字も落とさない・重複しない)。**これが F-1 の本体**。
3. 各 op の X が**単調増加**し、最初の op の X が `bodyX` と一致すること。
4. **サロゲートペアが分割境界で割れない**こと(境界にペアが跨る行を fixture にする)。
5. 選択色分けと同時に起きるとき、**3 run それぞれの内側で**分割されること。

> **ミューテーション検証の扱い**: CLAUDE.md §4-A は「GUI のレイアウト」を禁止領域とするが、
> `FrameBuilder` は**純レイアウト計算**(座標と文字列の算出)であり、テーマ適用でも
> イベントマッピングでもない。**2 と 4 に限り**、上限定数の off-by-one とスナップ落としの
> 変異が殺せることをスポットで確認する(§4-A 有効側の「選択範囲の算出」に近い性質)。
> 判断に迷うので、**レビューで否定されたら外す**。

### 2.7 やらないこと

- **可視範囲での切り出し**(案 B)。§2.3 のとおり別ブランチ。
- **描画コストの改善**。本修正は「描かれないものを描く」だけで、速くはならない。
- **上限の自動検出**(実際に `DrawText` が失敗したかを見る)。GDI は失敗を返さないので
  観測面が無い。定数で余裕を取る以上のことはできない。

### 5.1 最終ブランチレビュー(2 パス)で受容した項目 — 案 B へ回収する

2026-09-14 の最終レビューで挙がったもののうち、本ブランチでは直さず受容した項目。
**いずれも案 B(可視範囲での切り出し)で自然に解消する**ので、案 B のタスクに含める。

- **描画コストは極端な行で従来より増える。** §2.7 は「速くはならない」としか書いていないが、
  正しくは**遅くなる方向にも動く**。修正前は 1 個の巨大な `DrawText` を GDI が即座に捨てていた
  (実質無コスト)のに対し、修正後は `ceil(n / 16384)` 個の実描画が毎 `WM_PAINT` で走る。
  水平方向のカルは存在せず(`FrameBuilder.Build` に `scrollX` は渡らない)、
  `EditorControl.Paint.cs` の `textClipWidth = Math.Max(op.Width, ClientWidth - x)` は
  画面右外でも正値になるため矩形が空にならない。純 ASCII の長大行でのみ新たにコストが乗る
  (非 ASCII を含む行は `GdiCharMetrics.MeasureRun` が既に行全体を一括計測しており同程度)。
  → 案 B に**安価な水平カル**(累積 x が右端を超えたら以降の op 発行を打ち切る)を含める。
  分割が起きる行でのみ効かせれば、既存テストの `PaintOp` 列は不変のまま導入できる。
- **分割された選択 run は、継ぎ目のドリフトぶん文字が選択矩形からはみ出しうる。**
  非加算メトリクスではチャンク個別計測の合計が一括計測(= 矩形幅 `pxTo - pxFrom`)を上回るため、
  末尾の文字が塗られていない背景の上に `SelectionFore` で描かれる。
  ハイコントラストでは PR #75 が潰した「選択色の文字が背景に溶ける」と同じ失敗モードになる。
  発生条件は「16,384 文字超の run を選択」で極めて稀、かつ修正前は 1 文字も描かれなかったので受容。
- **結合文字クラスタは分割境界で割れる。** `SnapToCodePointStart` はサロゲートだけを見るので、
  ベース文字と結合マーク(U+0301 / U+3099 等)の間で分割されるとマークが単独 op になり合成されない。
  実害は 16,384 文字超の行の継ぎ目 1 箇所に限られる。
- **非分割経路で毎フレーム文字列コピーが 1 本増える**(`ReadOnlySpan<char>` 化に伴う
  `text.ToString()`)。非分割枝は定義上 16,384 文字以下で LOH に乗らないため受容。
  意識的な受容であることをここに残す(後の性能タスクで再発見しないため)。
- **累積 X の `int` オーバーフロー**(単一 ASCII 行が約 2 億 6,800 万文字超)。
  unchecked のため例外は出ず描画が崩れるだけで、既存の `MeasureRun` 内部累積にある同種欠陥の
  増幅にすぎない。水平カルが入れば自然に消える。
- **(既存)空白可視化オン時の `EmitWhitespaceGlyphs` が行長に対して O(n²)。**
  空白ごとに `PixelMapper.OffsetToPx` = 行頭からの prefix 計測を呼ぶため。
  数十万個の空白を含む 1 行でハングアップする。本ブランチ起因ではないが、
  `2026-08-02-large-line-resilience-design.md` の申し送りに挙がっていないので**ここで明示**する。
