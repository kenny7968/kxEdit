## 検証手法

- 発声は NVDA スピーチビューアーの本文を Win32 `WM_GETTEXT` で読み、
  操作前に文字数を控えて操作後の差分だけを取る(逐語・要約しない)。
- 目視は `PrintWindow(PW_RENDERFULLCONTENT)` でウィンドウ自身の描画を実解像度のまま取り込む
  (スピーチビューアーが重なっても判定できる。NVDA は昇格プロセスなので窓を動かせない)。
- キー送出は SendInput。矢印などの拡張キーには `KEYEVENTF_EXTENDEDKEY` を立てる。

### ハーネス側で踏んだ罠(製品の不具合ではない)

| 事象 | 原因 | 対処 |
|------|------|------|
| 矢印キーが設定ダイアログのタブを切り替えず、NVDA が 1 文字だけ読む | `WScript.Shell.SendKeys` が拡張キーフラグを立てない | SendInput 方式へ置換。windows-mcp の `Shortcut` で正常動作することを対照確認した |
| 設定ダイアログが二重に開いた | モーダルで無効化された親ウィンドウへ強制前面化してキーを送っていた | 送出前に `IsWindowEnabled` を検査し、無効窓には送らない |
| 本文のクリック(キャレット移動・ダブルクリック単語選択)が一切効かない | **クリック座標が NVDA スピーチビューアーの窓(34,57)-(518,493) に吸われていた**。`WindowFromPoint` で判明 | kxEdit のウィンドウを (520,4,500,720) へ移動して重なりを解消。移動後はクリックもダブルクリックも正常 |

**いずれも実ユーザーには到達できない経路。** 製品の判定には含めない。
3 つ目は一度「本文がマウスに反応しない」と誤判定しかけた。**目視・マウス系の判定前に
`WindowFromPoint` で最前面の窓を確認すること。**

# 検出した不具合

## F-1: 折り返し OFF で約 43,000 文字を超える論理行が一切描画されない

- **深刻度**: 高(晴眼・弱視ユーザーには本文が**真っ白**に見える。CLAUDE.md §2 の第一級要件)
- **再現**: 折り返し OFF のまま、1 行が 44,000 文字以上のファイルを開く。
- **観測**: 本文領域が完全な白。ステータスバーの行/桁・キャレット移動・NVDA の読み上げ・
  検索は**すべて正常に動く**ので、SR 経路だけ見ていると気付けない。
- **しきい値の実測**(`ＭＳ ゴシック 12pt` / 幅 960px):

  | 行長 | 描画 |
  |------|------|
  | 100 / 1,000 / 5,000 / 10,000 / 20,000 | される |
  | 24,000 / 28,000 / 30,000 / 32,000 / 32,767 / 32,768 / 33,000 / 36,000 / 40,000 / 42,000 | される |
  | 44,000 / 46,000 / 48,000 / 50,000 / 55,000 / 60,000 / 100,000 / 500,000 | **されない** |

- **切り分け**: 同じファイルでも**折り返しを ON にすると描画される**(視覚行が短くなるため)。
- **原因(コード読みによる推定)**: `FrameBuilder`(`src/kxEdit.Core/Layout/FrameBuilder.cs:182` 他)は
  視覚行のテキストを `snapshot.GetText(row.SegmentStartChar, row.SegmentLength)` で丸ごと取り、
  `EditorControl.Paint.cs:121` の `TextRenderer.DrawText` に**論理行全体をそのまま渡す**。
  折り返し OFF では視覚行 = 論理行なので、GDI が扱える長さを超えた時点で**黙って何も描かない**。
  可視範囲(水平スクロール位置 + クライアント幅)で切り出していないことが根因。
- **副次**: 同じ理由で、毎フレーム 500K 文字の文字列生成と計測が走る(既存の性能申し送りと同根)。

## F-2: 設定ダイアログを開いた直後、選択中のタブ名が読まれない

- **深刻度**: 低
- **逐語**: `設定  ダイアログ` / `タブコントロール` のみ。`基本  タブ  選択` が続かない。
- Tab で巡回して戻ってきたときや ←→ で切り替えたときは `基本  タブ  選択` まで読む。
  **初回フォーカス通知だけ**欠ける。

## F-3: NVDA 稼働中は挿入/上書きモードを切り替えられない

- **深刻度**: 中(SR 利用者だけが機能を使えない。CLAUDE.md §2 の「SR 対応エディタ」の中核)
- **再現**: NVDA を既定設定で起動し、kxEdit で Insert を押す。
- **観測**: 何も起きない。`MainForm.ToggleOvertype`(`MainForm.cs:1751`)が走らず、
  `挿入モード` / `上書きモード` の発声もステータスバーの通知更新も起きない。
- **原因**: NVDA は既定で Insert を自分の修飾キー(NVDA キー)として捕捉する
  (`%APPDATA%\nvda\nvda.ini` の `NVDAModifierKeys = 7` = CapsLock + テンキー Insert + 拡張 Insert)。
  kxEdit 側の `ProcessCmdKey` まで届かない。
- **代替手段が無い**: 編集メニューは 元に戻す / やり直し / 切り取り / コピー / 貼り付け /
  すべて選択 / 折り返し整形 の 7 項目だけで、**上書きモードの項目が無い**。
  他のキー割当も無い(`MainForm.cs` の `case Keys.Insert` が唯一)。
- **示唆**: メニュー項目(例 編集 → 上書きモード)か、NVDA と衝突しない別のキー
  (例 Ctrl+Shift+I)を足す。晴眼ユーザーは Insert で使えているので、
  **SR 利用者だけが使えない機能**になっている。

## F-4: 強制終了前に空だった「無題」タブが、セッション復元後に入力を受け付けない

- **深刻度**: 高(ユーザーは打っているつもりで 1 文字も記録されない。**NVDA は打鍵を読み上げるので
  SR 利用者は入力できたと誤認する**)
- **再現手順**(2 回とも再現):
  1. 設定で「起動時に前回開いていたファイルを開く」= ON、「文書のバックアップを有効にする」= ON。
  2. `Ctrl+N` で無題タブを作り、何か入力してから `Ctrl+A` → `Delete` で**空にする**。
  3. `Stop-Process -Name kxEdit -Force` で強制終了する。
  4. 再起動する。その無題タブがタブ列に復元される。
  5. そのタブで文字を打つ / `Ctrl+V` で貼り付ける / `Enter` を押す。
- **観測**: ステータスバーは `行 1, 桁 1` のまま。タブラベルに `*` が付かない。
  貼り付けも Enter も効かない。**ただし Space を押すと NVDA は `スペース` と発話する**
  (= 入力経路は生きているが、バッファが書き換わらない)。`EditorControl.ReadOnly` が
  立ったまま復元されているように見える。
- **対照(同じセッションで確認)**:
  - 中身のあった無題タブ(`* 無題 3`)→ **入力できる**
  - 復元されたファイルタブ(`a.txt`)→ **入力できる**
  - その場で作った `Ctrl+N` の新規タブ → **入力できる**
  - 空のまま復元された無題タブ(`無題 4` / `無題 5`)→ **入力できない**
- **示唆**: 復元経路(`FileController` の復元系 / `BackupCoordinator` の hot exit 復元)で
  `ReadOnly` を落とし忘れている枝がある疑い。空文書だけが踏むのは、
  復元時に本文を流し込む処理が**空だと早期 return** して `ReadOnly=false` の復帰まで
  到達していない、という形が考えられる(コード未確認・要調査)。
- **波及**: Issue #72 の L5 項目 12(起動直後のタブでの IME overlay 色)が**この不具合のせいで
  判定できない**。F-4 を直してから 12 を再実施する必要がある。
