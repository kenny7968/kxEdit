## 2. 現状の構造 — 「単語スパン」の実装が 2 つある

コードを追うと、N-3 と N-4 は独立した課題ではなく、**同じ 1 箇所が生む 2 つの症状**である。
リポジトリには単語に関する概念が 3 つ並存している。

| # | 概念 | 実装 | 規則 | 利用者 |
|---|---|---|---|---|
| 1 | **次の単語の頭** | `Core/Editing/WordBoundary.cs:60,97` | 文字クラス(8 分類・同一クラス連続 = 1 単語) | Ctrl+←→(`InputRouter.cs:160,171`)/ UIA `Move(Word)`(`TextRangeProviderV2.cs:303,312` → `UiaTextHostAdapter.cs:508-524`) |
| 2 | **単語の左端 / 右端** | `InputRouter.cs:539-568` | 文字クラス(1 を組み合わせて構成) | ダブルクリック単語選択 |
| 3 | **単語の左端 / 右端** | `UiaTextHostAdapter.cs:529-556` | **空白・CR・LF のみが区切り** | SR の読み上げスパン(`TextRangeProviderV2.cs:58-64` の `ExpandToEnclosingUnit(Word)`) |

**2 と 3 は同じ概念の 2 実装で、規則が食い違っている。** これが F-3 の正体である。
`Core/Editing/WordBoundary.cs:124-144` の `ClassOf` は Latin / Digit / Hiragana / Katakana /
Han / Other など 8 クラスに分けるが、3 は空白しか見ない。

### 予測される症状(採取前の仮説)

- **日本語では常にずれる。** `今日は晴れです` を例にすると、ダブルクリックは `今日` を選び、
  Ctrl+→ は `今日` → `は` → `晴` → `れです` と刻むのに、SR が読むスパンは
  **空白が無いので行全体**になる。
- **ASCII 英文(空白区切り)でだけ 2 と 3 が一致する。** これが今まで表面化しにくかった理由と
  考えられる。
- **同じ UIA ホストの中で 1 と 3 が混在する。** `Move(Word)` はクラス規則、
  `ExpandToEnclosingUnit(Word)` は空白規則。SR から見ると
  「移動した先で、移動単位と違うスパンを読まされる」形になる。
- **空白ゼロの長大行では 3 が行頭まで全走査する**(F-5)。
  `ExpandToEnclosingUnit(Word)` は `WordStart` と `WordEnd` を両方呼ぶため、
  1 操作あたり片道走査の 2 倍かかる。Core 側の同型実装 `PrevWordStart` は
  空白ゼロ 500K 文字で 1 回 1,393.5 ms の実測がある
  (`2026-08-02-large-line-resilience-design.md` §2.2)。

**F-3 を直すと F-5 の大半が同時に消える。** クラス規則なら日本語では数文字で止まるためである。
ただし `§9.8` の fixture のような Latin 一色 500K(= 同一クラスの長大連続)は救われない。
走査上限のキャップは別途要るか、という問いが残る。

これは棚卸し **F-4**(「文字」の数え方が 3 通り並存)の姉妹問題である。定義が散っていて、
どれが正かがコードから読み取れない。

## 4. 調査設計

成果物は `tests/yEdit.Editor.Smoke` の新サブコマンド `--wordunit` に集約する
(`LargeLineBench.cs` / `GdiBench.cs` と同じ 1 ファイル 1 ベンチの流儀)。
判定ゲートは持たず常に EXIT 0 とする(`--largeline` と同じ)。

**本番コードを直接叩ける。** `tests/yEdit.Editor.Tests/UiaTextHostAdapterClampTests.cs:19-22`
が示すとおり、`new EditorControl()` + `SetSource` + `(IUiaTextHost)ctrl` で Handle 生成なしに
UIA ホストの実装へ届く。素朴実装を再実装せずに実物を測れるため、
「同じ壊れ方をする参照は網にならない」という既知の失敗を踏まずに済む。
GDI を通らないので Form も不要である。

### 4.1 ずれの採取(N-4 の机上分)

短く目視可能な fixture について、**Ctrl+→ を繰り返したときの
(キャレット位置, SR が読むスパン, ダブルクリックで選ばれるスパン) の列**を出す。
単発の境界値より、この列の方が「移動は刻むのに読みは行全体」を一目で示せる。

fixture(いずれも 1 行・短い):

| 名前 | 内容 | 狙い |
|---|---|---|
| `ja` | `今日は晴れです。` | Han / Hiragana / Other の切り替わり。句点の扱い |
| `jakana` | `メモ帳のテキストを編集` | Katakana / Han / Hiragana の混在 |
| `en` | `foo bar baz` | 空白区切り = 2 と 3 が一致するはずの対照群 |
| `sym` | `foo(bar)=baz;` | 記号が Other クラスとして刻まれるか |
| `num` | `abc123def` | Latin / Digit の切り替わり |
| `wsp` | `今日　は` | 全角空白。`ClassOf` は U+3000 を Other 扱いにしている(`WordBoundary.cs:8` のコメント) |
| `emoji` | 絵文字を含む行 | サロゲートペアでの歩進 |

各行について、キャレット 0 から `NextWordStart` で右端まで進めながら次を記録する。

- 移動先(`WordBoundary.NextWordStart`)
- SR が読むスパン(`(IUiaTextHost)ctrl` の `WordStart` / `WordEnd`。
  `TextRangeProviderV2.cs:62-63` の `_end == _start` なら `NextChar` へ広げる分岐も再現する)
- ダブルクリックで選ばれるスパン(§4.3 の候補 A と同一構成)

### 4.2 コスト実測(N-3 の机上分)

空白・改行ゼロの長大行(`ascii` / `cjk`)× 100,000 / 500,000 / 2,000,000 文字で測る。
生成規則は `LargeLineBench.MakeSingleLine` を流用し、前後比較が成立するようにする。

| 測定項目 | 意味 |
|---|---|
| `WordStart(CharLength)` | 行末から行頭までの片道走査 |
| `WordEnd(0)` | 行頭から行末までの片道走査 |
| 合計 | `ExpandToEnclosingUnit(Word)` 1 回 = SR の単語読み 1 回分 |
| `WordBoundary.PrevWordStart`(参考) | 移動側。UIA 側が移動側の何倍かを出す |

ウォームアップ 1 回 + 3 回の最小値(`--largeline` / `--characcess` の流儀)。
2M で 1 条件が長すぎる場合に備え、`--largeline` と同じ打ち切り閾値を持たせる。

**この測定が N-3 の実機部分を代替する。** 実機セッション(§5)は「NVDA が UIA Word 単位を
使っているか」の裏取りに集中し、コストの数値は本ベンチで確定させる。
両者が取れれば「SR がこのコストを払っている」は合成で結論できる。
残る不確かさ(`Process.Responding` に現れるか等)は成果物へ申し送りとして残す。

### 4.3 候補評価(before / after)

同じ表に候補列を足す。

**候補 A — ダブルクリック選択が既に使っている規則へ揃える。**
`InputRouter.cs:539-568` の `PrevWordBoundary` / `NextWordBoundary` は、public な
`WordBoundary.PrevWordStart(snap, pos + 1)` と `NextWordStart` + 末尾空白の巻き戻しだけで
構成されている。ベンチでも同じ構成を public API から組める。

この候補の要点は「新しい規則を発明しない」ことである。**yEdit には既に
「単語の左端 / 右端」の出荷済み定義があり、UIA だけがそれを持っていない。**
揃えれば SR の読み上げが、目で見えるダブルクリック選択と一致する。

ただしベンチ内の再構成は `InputRouter` の private 実装との 2 実装同期になる。
**実際の修正では Core へ `WordBoundary.WordStart` / `WordEnd` として抽出し、
`InputRouter` と `UiaTextHostAdapter` の両方が同じ 1 本を呼ぶ形にする** —
これを候補 A の一部として成果物に明記する。

**候補 B — 走査上限キャップ。** `WordStart` / `WordEnd` の走査を N 文字で打ち切る。
候補 A では救えない「同一クラスの長大連続」(Latin 一色 500K など)に効く。
表には、キャップ N でスパンがどう変わるか、コストがどう落ちるかを並べる。

候補 A と B は排他ではない。§4.2 の実測を見て、A だけで足りるか A+B が要るかを判断する。

## 5. 実機セッション(ユーザー)

実機作業は 1 回に束ねる(PR #34 §4.3 と同じ単位設計)。載せるのは 2 件。

1. **N-4 の裏取りと実害採取。** NVDA スピーチビューアーを UIA で読む手法(PR #33 §9.8)で、
   §4.1 の fixture に対し Ctrl+←→ を押したときの発話を採取する。
   - 行全体を読むなら → **UIA Word 単位を使っている**(F-3 の実害あり)
   - クラス単位で切れるなら → **NVDA がクライアント側で分割している**(§6 の分岐へ)
2. **L5 未検証 3 項目の消化。** PR #34 から繰り越しているレビューカーソル / 上書きモード /
   音・点字。本題とは無関係だが実機起動のコストを共有できる。

§4.3 の候補列は、この場で「候補 A なら SR がどう読むことになるか」を人間が判断するための
材料としても使う(テキストと位置の表を手元に置いて発話と突き合わせる)。

## 6. 事前に決めておく分岐

PR #34 の最大の教訓は「否定命題は条件の同一性がすべて」であった。今回も
**採取結果がどちらに転んでも結論が書けるよう、分岐を採取前に確定しておく。**

| 実機の結果 | F-3 の位置づけ | 修正テーマの姿 |
|---|---|---|
| NVDA が行全体を読む | **実害確定。** 日本語の日常操作で常時ずれる | 候補 A(+ 必要なら B)。SR の読み上げ単位が変わる挙動変更 = 実装ブランチで L5 必須 |
| NVDA がクラス単位で切る | **SR 実害なし。** ただし UIA を叩く他クライアント(ナレーター等)には残る | F-3 は優先度を下げて監視へ。テーマは「F-5 のコストのみ」に縮み、候補 B 中心になる |

後者になった場合でも §4.2 のコスト実測は無駄にならない。`ExpandToEnclosingUnit(Word)` は
NVDA 以外の UIA クライアントからも呼ばれうるためである。
