## 2. 方針の分岐点と選択

L5 は 13 本分をまとめて 1 回で回すのが現実的で(監査 §8-5)、**実施後に src を触ると原理的に
やり直しになる**。したがって「L5 の前に src 修正をどこまで入れるか」が最初の意思決定になる。

- 案 A: すぐ L5 に入り、現状の main を確定版とみなす。最短でリリース可否が判る反面、
  **既知の虚偽発声とデータ破壊を抱えたまま**検証することになる。
- 案 B(**採用**): L5 を後回しにし、深刻度の高い修正を積んでから 1 回で回す。
  リリースは遠のくが、L5 の再実施リスクを最小化できる。

**ユーザー判断により案 B を採用**(2026-08-31)。

## 3. 本設計の芯 — 「Minor」ラベルを深刻度として読まない

監査 §6 の Minor 表は**発見時の分類であって深刻度ではない**。本設計の策定にあたり
残項目を実コードで再確認したところ、Minor 表の中に**データ破壊級**が混在していた。

### 4.1 順序の根拠

**B1 を最初に置く。** `tools/pre-merge-check.ps1:51` に
「Core.Tests の Debug は**足さない**: 既知 S-5 で 4 件赤になり、ゲートが常時 NG になる」と
明記されており、Core.Tests は Release 構成でしか走っていない(同 `:35-36`)。
`Debug.Assert` は `[Conditional("DEBUG")]` で Release バイナリに残らないため、
**Core の Debug 網はゲート上 1 行も走っていない**。

規模は正確に書いておく。`src/kxEdit.Core/` の `Debug.Assert` は実質 **8 サイト・2 ファイル**
(`Buffer/TextSnapshot.cs` 4 / `Editing/WordBoundary.cs` 4)であり、しかも WordBoundary の
4 サイトは **B1 自身が削除する対象**(2026-08-08 設計書 §3 案 A)。したがって Debug ステップ追加で
新たに守られるのは `TextSnapshot` の UTF-8 リードバイト/継続バイト検査 4 サイトである。
「以降 5 本が弱いゲートで走る」は**今ある網の量ではなく、B2〜B6 が Core に足す網が
最初からゲートに乗るかどうか**の話として読むこと。Issue #48 の最終レビュー Q-I-4 が
App.Tests で実証したとおり(`pre-merge-check.ps1:45-50`)、Release だけのゲートは
「網に見えるがゲート上は無効」という嘘の安全宣言を作る。

**B2 → B3 を隣接させる。** 両者は根因が異なる(B2 = 巻き込み境界、B3 = 範囲の陳腐化)ため
1 ブランチにはしない。**どちらも PR #56 が導入した道具立ての適用先であり、知見を引き継げる**
という理由で隣接させる。

**ただし「B2 の seam に B3 が乗る」わけではない**(レビュー I-1 で訂正)。B2 が足すのは
`ReplaceCharRangeExact` に「実際に書いた範囲」を問う**事後条件**の seam である。M-25 は
座標が陳腐化していても書込自体は「言われたところ」へ正しく落ちるため、この seam は
要求どおりの値を返し**陳腐化を検出できない**。B3 に要るのは編集開始時と commit 時の
**スナップショット世代の照合**(PR #56 §2.1 の `_lastHit` 世代付き化と同型)であって、
別の道具である。PR #56 設計書 §6 が「M-25 は本件では直らない」と書いているとおり。
**順序は入れ替えても作り直しにはならない。**

**B6 を最後に置く。** PR #57 の申し送りが
「`MarkdownPreviewForm.cs:89` を境界付きにすると監査 §9 の V-2(`.preview` の実 DNS 解決)を
踏ませる**可能性がある**」と指摘している。この 1 行の修正は V-2 の判断と**強く結合している**。
なお原理的に不可分ではない —— プローブがタイムアウトしたとき fail-open でマッピングを張る
(存在しないフォルダーへのマッピングは 404 で終わり DNS へは出ない)という逃げ道はある。
B6 でその選択肢ごと評価する。

B4 と B5 は他への依存がなく、B1 の後であればどこに置いてもよい。
