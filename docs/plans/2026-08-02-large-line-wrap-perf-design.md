# 巨大 1 行(折り返し ON × 非 ASCII)描画コスト解消 設計書

策定日: 2026-08-02 / 対象ブランチ: `feature/large-line-wrap-perf`

前提となる調査は `docs/plans/2026-08-02-large-line-resilience-design.md`(PR #34・マージコミット
`b28f378`)。本書はその申し送り **N-1** と **N-2** を対象とする。

## 1. 背景・目的

PR #34 の調査で、**折り返し ON × 非 ASCII × 長い論理行**という条件で
`LineLayout.Wrap` が 1 コードポイントごとに GDI `TextRenderer.MeasureText` を呼び、
CJK 500K 文字で `ComputeCaretPoint` 約 40 秒 + `OnPaint` 約 40 秒かかることが**実測で**
確定した(同設計書 §2.3)。`OnPaint` はフレームをまたぐキャッシュを持たないため、
再描画のたびに約 40 秒が再発する = 事実上、閉じるまで実用にならない。

既定設定(`WrapColumnEnabled=false`)では踏まないが、折り返しを ON にして日本語を含む
長い 1 行(1 行 JSON・整形前のログ等)を開けば誰でも踏む。

同時に、既存の性能ベンチ `GdiBench` が**画面外ウィンドウのため WM_PAINT が配送されず、
描画していない値で「平均フレーム時間 < 16ms」を PASS 判定していた疑い**が濃厚になった
(同 §2.3・申し送り N-2)。N-1 の改善効果を測る土台がこれである。

**目的**: N-2 で測定の土台を直し、N-1 の 40 秒を実用域へ落とす。

### スコープ外

F-1 / F-2 / F-3 / F-4 / F-5 / F-6、および N-3 / N-4 / N-5(いずれも実機 NVDA
セッションを要する観測タスク)は本ブランチで扱わない。申し送りとして §8 に残す。

## 2. 現状のコスト構造

`LineLayout.Wrap`(`LineLayout.cs:47-66`)は論理行を左から 1 コードポイントずつ走査し、
毎回 `metrics.MeasureRun(line.Slice(i, cpLen))` を呼ぶ。`GdiCharMetrics.MeasureRun`
(`GdiCharMetrics.cs:37-50`)は ASCII なら `_asciiWidths` の配列加算で返るが、
**非 ASCII を 1 文字でも含むと `text.ToString()`(span からの追加コピー)+
`TextRenderer.MeasureText` へ落ちる**。実測で 1 文字あたり約 80 µs。

無駄は独立した 2 種類がある。

| # | 無駄 | 内容 |
|---|---|---|
| **A** | **定数倍** | 同じ文字種を何度でも GDI で測り直す。日本語 500K 文字でも**異なるコードポイントは 2,000 種程度**しかない |
| **B** | **アルゴリズム** | `ViewportLayout.Build` も `ComputeCaretPoint` も、**可視 40 行しか使わないのに論理行全体を Wrap** する |

**A と B は独立で、どちらか一方だけでは足りない。**

- A のみ: 50 万回のループは残るが 1 回が辞書引き(約 25 ns)になる → 約 20〜40 ms/フレーム
- B のみ: 走査が約 3,200 文字に減るが 1 文字 80 µs のまま → 約 256 ms/フレーム(まだ遅い)
- A + B: 約 3,200 文字 × 25 ns → マイクロ秒級

なお `ComputeCaretPoint` は **O(キャレット位置)** であり、行末にキャレットがあると B は
効かない。そこは A が受け持つ。この非対称性が「両方入れる」根拠である。

## 3. 変更 1(N-2): `GdiBench` を実際に描画させる

`tests/yEdit.Editor.Smoke/GdiBench.cs:50` の `Location = new Point(-32000, -32000)` を
画面内へ移す。完全に画面外のウィンドウは可視領域が空になり、`Control.Update`
(`UpdateWindow`)が WM_PAINT を配送しない。調査では同条件の paint が
**1.0 ms → 33.2 ms** に変わった。

**修正前後の両方の数値を記録してから、16ms 基準の可否を判断する。** 直した途端に
ゲートが FAIL する可能性があるため、基準値の見直しをセットで行う(調査 §4 N-2)。
新基準は実測に基づいて決め、根拠を本書へ追記する。

### この変更を先に行う理由

これが N-1 の改善効果を測る土台だからである。測れないベンチのまま N-1 を入れると、
「速くなったことを検証する手段がない」まま進むことになる。

### 併せて記録する事実

`GdiBench`(`Editor.Smoke --bench`)は **`.github/workflows/bench.yml` / `tools/pre-merge-check.ps1` /
`tools/sr-regression.ps1` のいずれからも呼ばれていない**。`bench.yml` が実行するのは
`Core.Bench` の `--typing` / `--layout` / `--characcess` の 3 つのみである。
つまり N-2 は「測っていないのに合格していた」だけでなく「そもそも実行されていなかった」。
**自動ゲートへの接続は本ブランチのスコープ外**とし、事実の記録に留める(§8)。

### 実測値(Task 1 実施記録・2026-08-02)

条件はいずれも既定の `--mb 256`(140,460,434 文字 / 4,682,015 行)・Form 900×700・
1000 フレーム・Release ビルド。`Location` 以外は同一。

| | 平均フレーム時間 | max | 合計 | 判定 | EXIT |
|---|---|---|---|---|---|
| 修正前(`Location = (-32000,-32000)`) | **0.51 ms** | 1.09 ms | 1.0 s | PASS | 0 |
| 修正後(`Location = (100,100)`)1 回目 | **34.20 ms** | 41.19 ms | 35.1 s | FAIL | 1 |
| 修正後(`Location = (100,100)`)2 回目 | **34.24 ms** | 39.83 ms | 35.2 s | FAIL | 1 |

**約 67 倍**の差であり、修正前の値が描画コストをまったく含んでいなかったことを裏づける
(調査で観測した 1.0 ms → 33.2 ms と同じ桁の変化)。修正後は 2 回の再現で ±0.04 ms と安定。

**16ms 基準は変更しない。** これは実在の性能事実であり、しきい値を上げて通すことは
「測っていないのに合格」を「基準を緩めて合格」へ置き換えるだけになる。
FAIL(EXIT 1)のまま Task 2〜4 の改善を進め、基準の可否判断は Task 5 の最終実測まで保留する。
なお本ベンチはどの自動ゲートからも呼ばれていない(前節)ため、
FAIL のままでも CI / `pre-merge-check` は赤にならない。

## 4. 変更 2 + 3(N-1)

### 4.1 変更 A — `GdiCharMetrics` にコードポイント幅メモ化

`MeasureRun` に渡された span が**単一コードポイントのときだけ**、コードポイントを
キーとする `Dictionary<int, int>` を引く。ミス時は現在と同じ `TextRenderer.MeasureText`
を呼び、結果を格納する。**複数文字の run(水平スクロールバー算出経路)は現状維持**
(実測 12〜48 ms で無害・かつ run 全体の計測結果はコードポイント幅の和と一致するとは限らない)。

**性質**:

- **挙動完全不変** — 返す値は現在と同じ `MeasureText` の結果そのもの
- **無効化ロジック不要** — `GdiCharMetrics` はフォント単位で作り直される
  (`EditorControl.cs:145` の初期化・`:1681`〜`:1694` の `ApplyAppearance` で
  インスタンスごと差し替え)。キャッシュの寿命がフォントの寿命と一致する
- **初回コストは文書長ではなく文字種数で決まる** — 日本語なら 2,000 種程度 = 約 160 ms が
  1 度だけ。文書を長くしても増えない
- **メモリは有界** — BMP 全域を含む文書でも 65,536 エントリ

**⚠ スレッド前提が load-bearing になる。** `GdiCharMetrics` は「UI スレッド専用」と
クラスコメントに明記され、UIA RPC スレッドからは `Control.Invoke` でマーシャリング済み
(`UiaTextHostAdapter.cs:417-423` / `:431-450`)。この契約は現在も守られているが、
**破れたときの症状が変わる**。今は「幅がずれる」で済むところが、`Dictionary` は
非スレッドセーフなので**構造破損(無限ループ・例外)**になる。契約が守られていることの
再確認と、`GdiCharMetrics` 側へのコメント追記をタスクに含める。

### 4.2 変更 B — `Wrap` の早期打ち切り

既存の `LineLayout.Wrap` は据え置き、打ち切り可能な入口を追加する(既存 8 呼び出し元の
うち適用しないものは無改造で残るため、影響半径が閉じる)。

**正しさの根拠**: `Wrap` は左から右への貪欲な走査で、セグメント境界は**先行する内容だけ**で
決まる。したがって**打ち切り結果は完全な結果の prefix と厳密に一致する**。これは
テストで直接検証できる性質である(§5)。

打ち切り条件は 2 種類が必要:

- **セグメント数**による打ち切り — 可視高さを満たしたら止める(`ViewportLayout.Build`、
  `ComputeCaretPoint` の積み上げループ)
- **オフセット到達**による打ち切り — 指定オフセットを含むセグメントが確定したら止める
  (`ComputeCaretPoint` のキャレット行)

**⚠ 唯一の罠: 最終セグメントの特別扱い。** `EditorControl.cs:1540-1550` は
`segments.Count - 1` を既定値とし、`i == segments.Count - 1` のときだけ
「末尾ちょうど」を許容する(EOL キャレット位置)。打ち切ると「最後のセグメント」が
**真の最終セグメントとは限らなくなる**ため、この判定が壊れる。打ち切り版は
**「論理行末まで到達したか」を呼び出し側へ返し**、`ComputeCaretPoint` はそれを見て
特別扱いの可否を決める。ここが本変更で唯一、素直に書くと EOL キャレットの
サイレントなバグを生む箇所である。

### 4.3 変更 B を適用しない箇所とその理由

- **`UiaTextHostAdapter.cs:482`(SR 経路)** — 直上の `_lastLineSegs` が
  `(snap, line, wrap)` をキーに**完全なセグメント列**をキャッシュし、
  **別オフセットの照会にも使い回す**(`:463-468`)。部分リストを入れるとキャッシュが
  壊れる。SR 経路に触れずに済む副次的な利点もある
- **`VerticalNavigation` / `NavigationCommands` / `EditorControl.Input`(6 箇所)** —
  これらが重いという実測がない。YAGNI に従い触らない。必要になれば追加の打ち切り適用は
  §4.2 の API をそのまま使えるため、後追いのコストは低い

本節は**実施記録**であり、策定時スナップショットである §1〜§8 は書き換えていない
(CLAUDE.md §8)。§3 末尾の「実測値(Task 1 実施記録)」も残したままにしてある。

測定条件は全て同一機・Release ビルド・Form 900×700(`editor.ClientSize = 884×661`)・

### 9.1 Task 5 の fixture 追加

`MakeSingleLine` に kind を 2 つ足した(`Editor.Smoke --largeline` と `Core.Bench --largeline`
の両方・同一の生成規則・同一シード)。

| kind | 内容 | 追加理由 |
|---|---|---|
| `cjkwide` | CJK 統合漢字 U+4E00〜U+55FF の **2,048 種** | `cjk` は異なるコードポイントが 40 種しかなく、変更 A の初回コストが実文書(日本語で 2,000 種程度)より小さく出る |
| `emoji` | U+1F600〜U+1F64F の **80 種**(サロゲートペア) | 調査 §4 が N-1 の起票条件として明記。`TextBoundary.CodePointLengthAt` と `GdiCharMetrics` の UTF-32 キー経路を踏ませる |

既存の `ascii` / `cjk` / `mixed` は生成規則を変えていない(前後比較の成立が壊れるため)。
`switch` 式から `switch` 文への書き換えでも `Random` の消費順序は同一で、
同シード・同長で生成文字列がビット単位で一致することを別実装との突き合わせで確認した。

`emoji` は 1 コードポイント = 2 char なので `chars` は char 数であってコードポイント数ではない。
末尾の `ToString(0, chars)` がサロゲートペアの中間で切ることがあるが、`LineLayout` は
単独サロゲートを 1 code-unit として扱う契約(`LineLayoutTests.Lone_high_surrogate_is_treated_as_single_code_unit`)
なので測定は成立する。なお本ベンチの行長(100K / 500K / 2M)は全て偶数のため、
実際にはこの切り詰めは発生しない。

**新 kind は「改善前」を測っていない**(kind が存在しなかったため)。前後比較が必要になったら
変更 A / B を revert したビルドで測り直すこと。本記録は最終値のみの提示である。

Task 5 で fixture を触った後も `cjk` / `mixed` の値が Task 4 記録と ±2 ms で一致している
= 既存 kind の生成規則が実際に不変であることの実測的裏づけになっている。

### 9.3 `Core.Bench --largeline`(GDI 抜き・`MonoCharMetrics`)

`ViewportLayout.Build` の構造コスト(ms)。可視行数は 40 固定。

| kind | 100K wrap0 / wrap80 | 500K wrap0 / wrap80 | 2M wrap0 / wrap80 |
|---|---|---|---|
| `ascii` | 0.2 / 0.3 | 0.2 / 1.7 | 1.1 / 1.3 |
| `cjk` | 0.3 / 0.4 | 1.8 / 1.8 | 7.6 / 7.1 |
| `mixed` | 0.8 / 0.9 | 3.4 / 3.5 | 14.3 / 14.4 |
| `cjkwide` | 0.3 / 0.3 | 2.0 / 2.0 | 7.8 / 6.9 |
| `emoji` | 0.3 / 0.4 | 1.7 / 2.1 | 8.0 / 8.3 |

**wrap0 と wrap80 が同値**になった点が変更 B の直接の証拠である
(折り返し OFF は `WrapCore` 冒頭で単一セグメントを返して走査しない = 走査ゼロの基準線。
そこに wrap80 が並んだ = 折り返し ON の走査コストが可視分に閉じた)。

残っている行長比例のコストは `Wrap` ではなく **`ViewportLayout.cs:61` の
`snapshot.GetText(lineStart, lineLen)`**(論理行全体の string 化)である。
wrap OFF でも同額かかることがそれを示す。§9.7 の申し送りに回す。

### 9.4 変更 A と変更 B の効果の切り分け

`cjk` 500K / wrap 80 の paint で分解すると:

| 段階 | paint / フレーム | 差分の説明 |
|---|---|---|
| 改善前 | 39,855 ms | 50 万コードポイント × GDI 実測 約 80 µs |
| **A のみ**(Task 2) | 39.7 ms | GDI 実測が辞書引きになり **約 1,000 倍**。走査 50 万回は残る |
| **A + B**(Task 4) | 30.1 ms | 走査 50 万回 → 可視分(約 1,300 コードポイント)。**約 10 ms 減** |

- **A が主犯を殺し、B が残りを削った。** cjk 2M では B の寄与が大きく(68.9 → 35.7 ms)、
  A のあとに残る「走査回数 × 辞書引き」が行長に比例することと整合する。
- setSource 側(`ComputeCaretPoint`)への B の効果は 2M で 78.8 → 9.1 ms と大きい。
- **`mixed` だけ B がほぼ効かない**(153.7 → 147.6 ms)。残る 147 ms は Wrap ではなく
  **可視行ごとの GDI テキスト描画**だからである(§9.6 で内訳)。
- 設計 §2 が「A + B でマイクロ秒級」と見積もった点は**外れた**。§9.7 に記す。

### 9.5 文字種数の効果 — `cjk`(40 種)vs `cjkwide`(2,048 種)

| | 100K wrap80 | 500K wrap80 | 2M wrap80 |
|---|---|---|---|
| `cjk`(40 種) | 28.6 | 30.1 | 35.7 |
| `cjkwide`(2,048 種) | **45.8** | 27.0 | 32.4 |

- **定常状態では差が無い**(むしろ `cjkwide` の方がわずかに速い = 誤差の範囲)。
  文字種が 51 倍でも 1 フレームのコストは変わらない。
- 差が出るのは**最初の 1 条件だけ**。`cjkwide` の 100K wrap80 が 45.8 ms と突出しているのは、
  そこで初めて 2,048 種の幅メモを埋めるためである。`paintReps = 5` で割った値なので
  一度きりの追加コストは約 (45.8 − 27.0) × 5 ≒ **90 ms** と読める。
- 設計 §4.1 の「初回コストは文書長ではなく文字種数で決まる」は**正しい**。ただしその
  初回コストは実文書相当の文字種数でも **90 ms 程度の一度きり**で、定常フレームには現れない。
- ⚠ 本ベンチは 1 つの `EditorControl` を全条件で使い回すため `GdiCharMetrics` のメモが
  条件をまたいで生き残る。`cjkwide` の 500K / 2M が初回コストを払っていないのはそのためで、
  これは実アプリの挙動(メモの寿命 = フォントの寿命)と同じである。

### 9.7 `GdiBench` の 16ms 基準 — 判断材料(基準は変更していない)

**現在値**(いずれも本ブランチ最終形):

| `--mb` | 文書 | 平均フレーム | max | 判定 |
|---|---|---|---|---|
| 256(既定) | 140,460,434 文字 / 4,682,015 行 | **34.03 ms** | 41.49 ms | FAIL |
| 16 | 8,778,776 文字 / 292,626 行 | **33.94 ms** | 39.95 ms | FAIL |
| 1 | 548,691 文字 / 18,290 行 | **34.14 ms** | 40.15 ms | FAIL |

Task 1 の 34.20 / 34.24 ms と合わせて 5 回の測定が 33.9〜34.2 ms に収まる。

**判明したこと**:

1. **変更 A / B は `GdiBench` に効かない**(予測どおり)。`WrapColumns` 既定 = 0(折り返し OFF)・
   行番号 OFF・現在行強調 OFF なので、B(Wrap 打ち切り)は入る余地がなく、A(単一コードポイントの
   メモ化)も `FrameBuilder` が**行テキスト全体**を `MeasureRun` する経路(複数文字 run =
   メモ化対象外)しか通らない。
2. **34 ms は文書サイズにまったく依存しない。** 1MB → 256MB(**256 倍**)で 34.14 → 34.03 ms。
   つまり「巨大文書だから遅い」のではなく**1 フレームの描画そのものが遅い**。
   バッファアクセス・行インデックス・レイアウトはいずれも主因ではない。
3. **文書の形**: テンプレ 3 行(42 文字 ASCII / 27 文字 CJK / 16 文字 CJK+絵文字)の反復で
   **1 行あたり平均 30 文字**。可視行数は約 33 行。
4. **1 フレームの中身**: `FrameBuilder.cs:161-180` が可視行ごとに `snapshot.GetText(...)` +
   **行テキスト全体を `metrics.MeasureRun(text)`**、`EditorControl.Paint.cs:106-115` が
   同じ行を `TextRenderer.DrawText`。つまり **可視行数 × (GDI 実測 1 回 + GDI 描画 1 回)**。
   34 ms ÷ 33 行 ≒ **1.03 ms / 行**。
5. **1 行あたり 1 ms は `--largeline` の独立測定と一致する。** 同じ窓・可視約 33 行で
   wrap 80 の値を 1 行あたりに直すと:

   | 行の中身 | paint / フレーム | 1 行あたり |
   |---|---|---|
   | `ascii`(単一スクリプト) | 10.0〜11.9 ms | 0.30〜0.36 ms |
   | `emoji`(単一スクリプト・サロゲート) | 18.8〜23.9 ms | 0.57〜0.72 ms |
   | `cjk` / `cjkwide`(単一スクリプト) | 27.0〜35.7 ms | 0.82〜1.08 ms |
   | **`mixed`(ASCII と CJK が 1 文字おき)** | **146〜158 ms** | **4.4〜4.8 ms** |

   `GdiBench` の 1.03 ms/行 は CJK 行の実測値そのものである。
   **`mixed` の突出は文字数では説明できない**(`mixed` の行は `cjk` の行より
   1.3 倍程度しか文字が多くない)。GDI 抜きの `Core.Bench` でも `mixed` は `cjk` の
   2 倍だが、そちらは行全体の `GetText` 側のコストである。したがって残る差は GDI 側にあり、
   **1 行内のスクリプト遷移**が有力な説明だが、GDI 内部の内訳までは本タスクで追っていない。

**所見(判断はユーザーに委ねる)**:

- **16ms は「描画していない値」に対して置かれた基準であり、実描画に対して検証されたことが
  一度もない。** 900×700 / MS ゴシック 12pt という本ベンチの条件では可視 33 行になり、
  **全 ASCII の理想ケースですら 33 行 × 0.3 ms ≒ 10〜12 ms** で 16ms にほとんど余裕がない。
  日本語や絵文字を含む文書では現在の「行ごとに GDI 実測 1 回 + 描画 1 回」方式のままでは届かない。
  実際のユーザーは最大化ウィンドウ = より多くの可視行で使うため、条件はさらに厳しくなる。
- **34 ms が何のコストか**: 可視行ごとの GDI テキスト API 呼び出し(実測 + 描画)。
  文書サイズ・レイアウト・折り返しはいずれも関与しない。
- **直すとしたらどこか**(いずれも本ブランチ未検証の候補):
  1. `FrameBuilder.cs:168` の `metrics.MeasureRun(text)` — 描画 1 回につき実測 1 回が必ず付く。
     この幅は `PaintOp.Width` = `TextRenderer.DrawText` の矩形幅として使われ、矩形は
     クリップとしてしか効かないので、可視幅で頭打ちにできる可能性がある。
     ⚠ ただし `_lastFrame` は「Uia 座標 API 用のスナップショット」として保持されている
     (`EditorControl.cs:112-114`。現状 src 内で読んでいるのはテストフックのみ)。
     幅を変えるなら `Frame` の消費側を先に棚卸しすること。
  2. **フレーム間キャッシュが無い** — `(snapshot, topLine, wrapColumns, size)` が同じなら
     `Frame` を再利用できる。`GdiBench` は毎フレーム `TopLine` を変えるので効かないが、
     実アプリのキャレット点滅・フォーカス往復・オーバーレイ再描画には効く。
  3. GDI(`TextRenderer` = Uniscribe)自体のスクリプト遷移コスト。根治は描画エンジンの
     置き換え(グリフキャッシュ / DirectWrite)になり、桁の違う話になる。
- **基準は上げていない。** Task 1 の判断(§3)をそのまま維持し、FAIL のまま据え置く。
  本ベンチはどの自動ゲートからも呼ばれていないため CI / `pre-merge-check` は赤にならない。

**測定中に観測した別件**: `--mb 16` の実行で、結果出力後の後片付けで
`InvalidOperationException:「CreateHandle() の実行中は Dispose() を呼び出せません」`
(`GdiBench.cs:87` の `using` による `Form.Dispose`)が 1 回だけ発生した。
測定値の出力後なので数値には影響しないが、`form.Close()` の直後に `using` の `Dispose` が
走る構造で間欠的に起きる。本ブランチで触っていない既存コードのため記録に留める。

### 9.8 設計時の想定と実測が食い違った点

1. **§2 の「A + B で約 3,200 文字 × 25 ns → マイクロ秒級」は外れた。**
   実測は 20〜30 ms / フレームである。原因は見積りの誤りではなく**見積りの範囲**にある。
   §2 のコスト構造表は `LineLayout.Wrap` しか勘定に入れておらず、
   **可視行ごとの GDI 実測 + 描画**(`FrameBuilder` / `RenderFrame`)というフレームの
   固定コストが表に入っていなかった。皮肉なことに §2 の「A のみ = 約 20〜40 ms/フレーム」は
   **A+B 後の実測とほぼ一致している**が、これは偶然の一致であって内訳は違う。
2. **`mixed` が最悪条件になるとは想定していなかった。** 設計は「非 ASCII を含むか否か」で
   コストが決まると考えていたが、実測では `mixed`(147 ms)が `cjk`(30 ms)の約 5 倍になる。
   GDI 抜きの `Core.Bench` でも `mixed` は `cjk` の 2 倍(2M で 14.4 vs 7.1 ms)だが、
   そちらは行全体の `GetText`(UTF-8 デコード)のコストであって折り返しではない。
   構造側で説明できるのは 2 倍まで = **残る差は GDI 側(1 行内のスクリプト遷移)**
   と読むのが自然だが、GDI 内部の内訳までは本タスクで追っていない。
3. **変更 B は `Wrap` の走査しか打ち切らない。** `ViewportLayout.cs:61` は依然として
   `snapshot.GetText(lineStart, lineLen)` で**論理行全体を string 化**するため、
   行長比例のコストが残る(`Core.Bench` の GDI 抜きで 2M 文字 = 7〜14 ms)。
   設計書 §4.2 はこの残差に言及していなかった。
4. **折り返し OFF の長大 1 行には A も B も効かない。** wrap OFF では可視行 = 論理行全体に
   なるため `FrameBuilder` が行全体を実測 + 描画する(`cjk` 2M / wrap 0 で 31.8 ms/フレーム)。
   N-1 の対象は折り返し ON だったので範囲内の判断ではあるが、**「巨大 1 行が重い」問題は
   折り返し OFF 側にも別経路で残っている**。
5. **`GdiBench` の 16ms は「改善で届く」類の差ではなかった。** §3 は「Task 5 の最終実測まで
   判断を保留」としたが、実測の結論は「本ブランチの変更とは無関係な、別のコスト構造」である
   (§9.7)。
