# 巨大 1 行 / 長大トークン耐性 — 真因切り分け調査 設計書

策定日: 2026-08-02 / 対象ブランチ: `feature/large-line-triage`

## 1. 背景・目的

PR #33(文字アクセス seam 集約・マージコミット `a12513c`)の L5 実機 SR 検証で副産物が
見つかった。**500KB の空白・改行を一切含まない 1 行ファイルを開くと、UI が 240 秒経っても
応答しない**(`docs/plans/2026-07-31-char-access-seam-design.md` §9.8)。同じファイルで
着手前の `main` をビルドしても同じくハングしたため、PR #33 が原因でも PR #33 で解消された
ものでもない**既存問題**である。

同時に、同設計書 §8 に申し送り F-1〜F-6 が積み上がった。本調査の目的は 2 つ。

1. 副産物の**真因を確定**し、対応規模を見積もれる状態にする
2. 申し送りを**棚卸し**し、対応要否・順序・単位を確定する

**本ブランチは調査に限定し、`src/` を一切変更しない。**

## 3. なぜ「調査」を独立させるか

§9.8 の記述は「主因は §8 F-5 に併記した折り返し ON × 改行なし巨大 1 行と**見られ**」という
推定止まりである。加えて、コードを読むと**推定と噛み合わない事実**がある。

- `GdiCharMetrics.MeasureRun`(`GdiCharMetrics.cs:37-50`)は、**全文字が ASCII なら
  `_asciiWidths` の加算だけ**で返る。GDI(`TextRenderer.MeasureText`)へ落ちるのは
  非 ASCII を 1 文字でも含むときのみ。
- したがって fixture が ASCII(base64 等)なら `LineLayout.Wrap` も水平スクロールバー算出も
  理論上ミリ秒級であり、**240 秒を説明できない**。
- 逆に fixture が非 ASCII なら、`LineLayout.Wrap` は**1 コードポイントごとに `MeasureRun` を
  呼ぶ**(`LineLayout.cs:50-52`)ため、500K 文字 = 500K 回の GDI 呼び出しになる。

**真因は fixture の文字種で分岐する。** そして §9.8 には fixture の中身(文字種)が
記録されていない。ここを確定せずに設計へ進むと、F-1 `CharCursor`(文字アクセス層)で
解決するつもりが**レイアウト層の問題だった**という空振りになる。§9.8 自身も
「文字アクセスの高速化では解消しない」と書いており、PR #33 のスコープ外だったことは
確認済みである。

## 4. 調査設計

### 4.1 Task 1 — 「ファイルを開く」経路のコードリーディング

論理行全体を舐める箇所を列挙し、**1 回のファイルオープンで何回呼ばれるか**を確定する。
コスト = 1 回あたりの重さ × 呼び出し回数であり、後者を落とすだけで解決する可能性があるため、
回数の確定を成果物に含める。

既知の候補:

| 箇所 | 何をするか | 巨大 1 行でのコスト |
|---|---|---|
| `ViewportLayout.cs:53-55` | 論理行全体を `GetText` して `LineLayout.Wrap` | 可視分での打ち切りは**セグメント確定後**。行全体の Wrap は避けられない |
| `EditorControl.cs:1072-1083` | 水平スクロールバー算出。`wrapColumns: 0` で `Build` → 行全体を `GetText` して `MeasureRun` へ一括投入 | 500K 文字 string 生成 + GDI 一括計測 |
| `EditorControl.Paint.cs:34` | 描画のたびに `ViewportLayout.Build` | **フレームごとに再計算**(キャッシュなし) |
| `EditorControl.cs:1528-1533` | キャレット位置 → 視覚セグメント解決 | 同上 |
| `VerticalNavigation.cs:215-216` | 論理行の視覚行数カウント | 上下移動のたび |

成果物: **呼び出し回数つきの経路表**。

### 4.2 Task 2 — ベンチ追加(`--largeline`)

`tests/yEdit.Core.Bench` に `--largeline` を追加する(既存オプションは `--layout` /
`--typing` / `--characcess`)。

測るもの:

- 候補経路ごとのコスト。**fixture の文字種を ASCII / CJK / 混在で振る**(§3 の分岐を潰す)
- 行長を 100KB / 500KB / 2MB で振り、**線形か O(n²) か**を判定する
- **F-6 の空白を埋める** — `AppendBuffer` 現ブロック経路(`TextBuffer.FromString` ではなく
  実際にタイプして育てた文書)での `GetChar` / 単語ナビ。既存 `--characcess` はこの経路に
  一度も触れていないため、§9.2 の数値は読み込み済み文書に対するものに限られる

`LineLayout` / `ViewportLayout` は `internal` のため、Bench から直接叩けるかを最初に確認する
(叩けなければ §8 R2 に従い Editor 層へ寄せる)。

### 4.3 Task 3 — 実機セッション(1 回・ユーザー)

自動では取れない 2 つをまとめて実施する。実機作業を 1 回に束ねるのが本ブランチの単位設計の肝。

1. **副産物の裏取り** — 長大 1 行ファイルを開き、`Process.Responding` をポーリングして
   復帰までの実時間を測る。**`SendKeys` の所要時間は無効**(ハングしたウィンドウのメッセージ
   キューに投げて即座に返るため。§9.8 で実際に 10.5 ms という無効値を得た)。
   **折り返し ON / OFF の両方**で測り、`ViewportLayout` 経路の寄与を切り分ける。
   §9.8 で使った fixture の**文字種を記録する**(§3 の分岐に直結)。
2. **F-3 の実害採取** — NVDA スピーチビューアーの `RICHEDIT50W` ペインの `Name` プロパティを
   UIA で読む手法(§9.8 で確立)により、「同じ位置なのに SR の単語読みと Ctrl+←→ の移動先が
   違う」実例を **CJK / 記号 / 英単語 / 混在**で採取する。

任意: L5 未検証 3 項目のうち**レビューカーソル**と**上書きモード**も同セッションで消化してよい。

### 4.4 Task 4 — 成果物

`docs/plans/2026-08-02-large-line-resilience-design.md` を新設し、Task 1〜3 の結果を
§1 背景 / §2 現状調査として記述する。**スコープ以降は書かず、ユーザーへ判断を仰ぐ。**
本調査の役割は判断材料を揃えるところまでである。

## 5. 検証手法上の注意(既知の罠)

PR #33 で実際に踏んだもの。再発させない。

- `SendKeys` の所要時間は処理完了までの時間ではない → `Process.Responding` をポーリングする
- 単一位置での測定は格子セル内オフセットで最大 20 倍変わる → セル全域を掃く
- `results.All(r => r.Pass is not false)` は判定行ゼロで空真 = **測っていないのに合格**を出す
- 前後比較のため**旧版をビルドして同じ操作を流す**(§9.8 で `main` と比較し既存問題と確定させた手法)
- 並行でエージェントを走らせるならワークツリーを分離する(マシン負荷で絶対値が 10 倍ずれた実例)
