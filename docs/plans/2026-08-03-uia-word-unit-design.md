## 2. 調査結果

### 2.1 単語スパンの実装が 2 つある

リポジトリには単語に関する概念が 3 つ並存している。

| # | 概念 | 実装 | 規則 | 利用者 |
|---|---|---|---|---|
| 1 | 次の単語の頭 | `Core/Editing/WordBoundary.cs:60,97`(public) | 文字クラス 8 分類 | Ctrl+←→(`InputRouter.cs:160,171`)/ UIA `Move(Word)`(`TextRangeProviderV2.cs:303,312`) |
| 2 | 単語の左端 / 右端 | `InputRouter.cs:539-568`(private) | 文字クラス(1 を組み合わせて構成) | ダブルクリック単語選択 |
| 3 | 単語の左端 / 右端 | `UiaTextHostAdapter.cs:529-556`(private) | **空白 / CR / LF のみ** | SR の読み上げスパン(`TextRangeProviderV2.cs:58-64`) |

**2 と 3 は同じ概念の 2 実装で、規則が食い違っている。** これが F-3 の正体である。
1 は別概念なので、UIA の中でも `Move(Word)` はクラス規則、`ExpandToEnclosingUnit(Word)` は
空白規則という**混在**が起きている。

### 2.2 ずれの実態(机上採取)

`--wordunit` の §4.1 表より。「Ctrl+→ を繰り返したときに SR が読むスパン」と
「同じ位置でダブルクリックしたときの選択」を並べたもの。

| fixture | 結果 |
|---|---|
| `今日は晴れです。` | **全 5 位置でずれ**。キャレットは 0→2→3→4→7→8 と刻むのに、SR スパンはどの位置でも `[0,8)` = 行全体 |
| `メモ帳のテキストを編集` | **全 6 位置でずれ**。同上、`[0,11)` = 行全体 |
| `foo bar baz` | **全 3 位置で一致**(対照群) |
| `foo(bar)=baz;` | **全 6 位置でずれ**。`[0,13)` = 行全体 |
| `abc123def` | **全 3 位置でずれ**。`[0,9)` = 行全体 |
| `今日　は` | 3 位置中 1 つでずれ。**逆向き** — 全角空白の上(pos=2)で SR は `[0,2) 今日` = **キャレットを含まないスパン**を返す |
| `あ😀い😀う` | **全 5 位置でずれ**。`[0,7)` = 行全体 |

**「日本語だけの問題」ではない。** `foo(bar)=baz;` も `abc123def` も全行ずれる。
一致条件は「空白区切りだから」ではなく **「非空白 run が単一文字クラスで構成されるから」**である
(`今日　は` の pos=0 / pos=3 も一致するのがその証拠)。

全角空白の逆向きずれは `char.IsWhiteSpace(U+3000) == true` なのに
`WordBoundary.ClassOf` が U+3000 を `Other` に分類する(`WordBoundary.cs:8,131-132`)ことに由来する。

### 2.3 ★ 実機 NVDA での挙動(N-3 / N-4 の核心)

2026-08-03 実施。NVDA 稼働(`nvda.ini`: `keyboardLayout = laptop` / `NVDAModifierKeys = 7`)。
発話は NVDA スピーチビューアーの `RICHEDIT50W` から Win32 `WM_GETTEXT` で採取した。

| 行 | 操作 | NVDA の発話 | §2.2 の予測 | 一致 |
|---|---|---|---|---|
| `今日は晴れです。` | Ctrl+→ ×3 | 毎回 `今日は晴れです。` | どの位置でも `[0,8)` = 行全体 | ✓ |
| `foo bar baz` | Ctrl+→(0→4) | **`bar`** | `[4,7) bar` | ✓ |
| `foo(bar)=baz;` | Ctrl+→(0→3) | `foo(bar)=baz;` | `[0,13)` = 行全体 | ✓ |
| `abc123def` | Ctrl+→(0→3) | `abc123def` | `[0,9)` = 行全体 | ✓ |
| `今日　は` | Ctrl+→(0→2) | `今日` | `[0,2)`(キャレットを含まない) | ✓ |

**対照群 `foo bar baz` が単語単位で切れたことが決め手である。**
「NVDA は単に行を読んでいるだけ」という対立仮説なら英語行も行全体になるはずで、そうならなかった。
**NVDA は yEdit の `ExpandToEnclosingUnit(Word)` の戻り値をそのまま読んでいる**
= 設計書 §6 の分岐は前者(**F-3 の実害確定**)。

さらに、同一セッション・同一位置で 2 つの「単語」が併存することを実演できた。

| 操作 | NVDA の発話 |
|---|---|
| `今` をダブルクリック | `今日 選択`(2 文字) |
| 同じ行で Ctrl+→ | `今日は晴れです。`(8 文字 = 行全体) |

**目で見える選択と耳で聞くスパンが食い違う。** SR を使わなくても確認できる症状である。

### 2.4 コストの実態(N-3)

`--wordunit` の §4.2 表より。空白・改行ゼロの単一長大行。
`ExpandToEnclosingUnit(Word)` 1 回 = `WordStart` + `WordEnd` の片道 2 回分。

| kind | 100,000 | 500,000 | 2,000,000 |
|---|---|---|---|
| ascii | 549.4 ms | **2,761.7 ms** | 11,099.0 ms |
| cjk | 389.5 ms | 1,933.8 ms | 7,779.2 ms |
| jamix | 384.2 ms | 1,947.3 ms | 7,826.7 ms |

行長に線形。`ascii` の移動側 `PrevWordStart` は 277.4 / 1,383.4 / 5,597.2 ms で、
既存実測(`2026-08-02-large-line-resilience-design.md:182-186` の 274.0 / 1,393.5 / 5,587.7 ms)と
**1.5% 以内で一致**する(fixture の生成規則とシードを既存ベンチへ揃えたため同一条件の比較)。

**N-3 の結論**: §2.3 で NVDA が UIA Word 単位を使うことが確定したので、
**SR はこのコストを実際に払っている**。空白ゼロ 500K 行では単語読み 1 回あたり約 1.9〜2.8 秒。

> 残る不確かさ: 本セッションでは長大行 × SR での `Process.Responding` を測っていない。
> UI スレッド同期 `Invoke`(`UiaTextHostAdapter.cs:578` / `:708`)がどう効くかは未検証。
> 実装ブランチの L5 で前後比較すれば済むので、単独の課題としては追わない。

### 2.5 修正候補の評価

`--wordunit` の §4.3 表より。**候補は本番 `src` ではなくベンチ内で構成**し、
写経が本物と一致することを `SelfCheck` で毎回確認している(候補 A は `InputRouter` の
private 実装を反射で、候補 B は cap 無制限で `(IUiaTextHost)` 経由の本物と全 pos 照合)。

| kind | 現状 | 候補A(クラス規則) | 候補B(cap=1000) | 現状/A | 現状/B |
|---|---|---|---|---|---|
| ascii 500K | 2,762.4 ms | 2,772.3 ms | 7.19 ms | **1.0x** | 384x |
| cjk 500K | 1,926.3 ms | 1,928.2 ms | 4.37 ms | **1.0x** | 441x |
| jamix 500K | 1,931.6 ms | **0.004 ms** | 4.27 ms | **449,199x** | 452x |

**候補 A は「現実的な日本語」にしか効かない。** `ascii`(全 Latin)/ `cjk`(全 Hiragana)は
単一クラスの長大連続なので、クラス規則を当てても走査距離が変わらず **1.0x** にとどまる。
効果が見えるのはクラスが交替する `jamix` だけである。
この非対称を測るために本調査で `jamix` kind を新設した。

**候補 B は単体では採用できない。** 理由が 2 つある。

1. **キャレットを含まないスパンを返す。** `WordStart(pos)` が `pos - cap` を返し
   `WordEnd` がそこから cap 歩進むため、行中央 pos=250,000 での expand は
   `[249,000, 250,000)` = キャレット位置の手前で終わる。
2. **壁時計時間が定数にならない。** 歩数は cap で定数だが、`TextSnapshot.GetChar` のコストが
   `TextChunk` の格子(`TextChunk.cs:28` の既定 4KB)内の線形走査に比例するため、
   実コストは `行長 mod 格子幅` の位相で数倍振れる(ascii の 3.23 / 7.19 / 1.85 ms が実例で、
   行長に単調でない)。

なお **候補 B は `Move` / `NextWordStart` 経路には影響しない**(`TextRangeProviderV2.cs:303,312`)。
変わるのは expand が返すスパンだけで、SR が行を単語送りする回数は変わらない。

## 3. 修正方針

### 3.1 結論

**候補 A を採る。単一クラス長大連続への上限は、候補 B の欠陥を直した形で A の上に載せる。**

具体的には次の 3 点。

1. **Core に `WordBoundary.WordStart` / `WordEnd` を新設する。**
   規則は既存の文字クラス規則(= ダブルクリック単語選択が既に使っているもの)。
   新しい規則を発明しない。
2. **3 箇所が 1 本を共有する形にする。**
   `InputRouter.cs:539-568` の private 2 メソッドと `UiaTextHostAdapter.cs:529-556` の
   素朴実装を、新設した Core の 1 本へ統合する。§2.1 の「同じ概念に 2 実装」を構造的に解消する。
3. **走査上限は「キャレットを含む窓」にする。**
   `[pos - cap, pos + cap]` を単語 run と交差させる形にすれば、候補 B の欠陥 1
   (キャレット除外)は構造的に起きない。cap 値は別途決める — 1,000 文字は
   SR が読み上げる「単語」としては既に長すぎるので、より小さい値を検討する。

### 3.2 なぜ候補 A が「安全側」か

**英語ユーザーの体験は変わらない。** §2.2 の対照群 `foo bar baz` が示すとおり、
空白区切りで単一クラスの run は現状と候補 A で完全に一致する。
変わるのは日本語・記号混じり・数字混じりの行だけである。

**変更後のスパンは既に出荷済みの挙動と一致する。** ダブルクリック単語選択がそれで、
晴眼ユーザーは日常的にその単位を見ている。SR の読み上げをそこへ揃えることになる。

### 3.3 未確定の点(実装ブランチで決めること)

- **cap 値。** §2.5 のとおり壁時計は cap に単純比例しないので、cap を決めるには
  実装ブランチで測り直しが要る。
- **日本語をクラス単位で刻むのが快適か。** 本調査で確認したのは「現状は行全体が読まれる」
  ことであって、「クラス単位が良い」ことではない。`今日` / `は` / `晴` / `れです` という
  刻み方が SR 利用者にとって自然かは **L5 で確認する**。
- **`ClassOf` が U+3000 を `Other` に分類する件**(§2.2 の逆向きずれ)。
  候補 A ではキャレット位置の全角空白そのものが 1 単語として返るので現状より正確になるが、
  全角空白を Whitespace 扱いに変えるかは別問題として残る。

### 3.4 L5 の要否

**必須。** SR の読み上げ単位が変わる挙動変更である(CLAUDE.md §5)。
`ExpandToEnclosingUnit(Word)` は §2.3 で NVDA が実際に使っていることを確認済みなので、
「SR 経路に触れるか」の判定に迷う余地はない。

## 4. 副次的に判明したこと

### 4.1 `IUiaTextHost` の doc コメントが事実と違う

`src/yEdit.Accessibility/IUiaTextHost.cs:57-61` は `WordStart` / `WordEnd` を
**「Core WordBoundary 委譲」**と書いているが、実際は `UiaTextHostAdapter` の素朴実装である。
同ファイルの `NextWordStart` / `PrevWordStart`(`:63-67`)は本当に委譲しているため、
**4 つのうち 2 つだけが嘘**になっている。§3.1 の統合で doc と実装が一致する。

### 4.2 「単語」の定義の散逸は F-4 の姉妹問題

棚卸し **F-4**(「文字」の数え方が 3 通り並存)と同型である。
どちらも「同じ言葉が指すものが実装ごとに違う」問題で、
§3.1 の統合は F-4 と同じ方向の是正になる。

### 4.3 ★ L5 相乗りの発見 — 上書きモードに SR ユーザーが到達できない

`docs/plans/2026-07-06-p6-manual-checklist.md:52` の D-6
(`Insert` キーで挿入/上書きトグル・「上書きモード」/「挿入モード」と発声)を検証した結果、
**NVDA 稼働下ではトグルが発火しない**。

- SendKeys で `{INS}` を送っても「上書きモード」の発声がなく、
  Ctrl+Alt+P の現在位置照会にも「、上書き」が付かない(`行 803 / 全 803、桁 1`)。
  `MainForm.cs:889-895` は両方を実装しているので、**Insert が yEdit に届いていない**。
- 原因は NVDA 設定 `NVDAModifierKeys = 7` = numpad Insert / 拡張 Insert / CapsLock の
  **すべてが NVDA 修飾キー**。拡張 Insert は NVDA に消費される。
- `ToggleOvertype()` の呼び出し元は `MainForm.cs:530` の Insert キーのみで、
  **メニュー導線がない**。したがってこの構成の NVDA ユーザーには
  **上書きモードへ入る手段が存在しない**。

留保: NVDA 側で Insert を修飾キーから外せば届くので、yEdit 単独のバグではなく衝突である。
ただし**代替導線が無い**のは yEdit 側で塞げる。モード(M) メニューへ項目を足すのが最小の対策。

**別テーマとして起票すべき。** 本ブランチのスコープ外。

## 6. 手法メモ(次に実機採取をする人へ)

- **NVDA スピーチビューアーの `RICHEDIT50W` は `TextPattern` を持たない。**
  `ValuePattern` は**先頭 4096 文字**で切り詰められるため、そのまま使うと
  1 時間前の発話を読んで「新しい発話が来ていない」と誤判定する。
  **Win32 `WM_GETTEXT` で全文を取ること**(本調査では 93,413 文字が取れた)。
- **windows-mcp は Insert 修飾を送れない。** `insert+o` は素の `o` 入力になる。
  NVDA ジェスチャ(NVDA+キー)を要する検証には使えない。
  **修飾キーが効いているかを、届いたら分かる操作で先に確かめること。**
- **Windows PowerShell 5.1 は `-File` 実行時にスクリプト全体を先に構文解析する。**
  同一スクリプト内で `Add-Type` しても型リテラルは解決できない。
  **先に `Add-Type` してから dot-source する。**
- **否定命題には対照群を置く。** 「日本語行で行全体が読まれた」だけでは
  「NVDA が UIA Word 単位を使っている」と「NVDA が単に行を読んでいる」を区別できない。
  `foo bar baz` が単語単位で切れたことが決め手になった(§2.3)。
