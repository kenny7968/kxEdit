## 3. M-8 — 窓外 Raise が保留 trailing を取り消さない

### 3.1 再現(実コードから確定)

`UiaAnnouncer.Say` は 3 経路に分かれる。空文字列(`:53-65`)は pending を潰す。窓内(`:71-83`)は
pending へ buffer する。**窓外(`:85-89`)は `_lastSaidUtc` を更新して即 Raise するだけで、
armed 済みの trailing timer にも `_pendingMessage` にも触れない。**

| 時刻 | 呼び出し | 起きること |
|------|---------|-----------|
| T=0 | `Say("a")` | 窓外 → 即 `Raise("a")`。`_lastSaidUtc=0` |
| T=20 | `Say("b")` | 窓内 → `_pendingMessage="b"`・timer を T=70 へ armed |
| T=60 | `Say("c")` | 窓外(60−0=60 ≧ 50)→ 即 `Raise("c")`。**pending="b" と timer は生存** |
| T=70 | trailing 発火 | **`Raise("b")`** ← 最後に読まれるのが 1 つ前 |

監査の「CSV で → 押しっぱなし」はこの形。キーリピートが throttle 窓(50 ms)をまたぐ間隔で
届くと、窓内 Say と窓外 Say が交互に来て pending が置き去りになる。

### 3.2 修正

窓外分岐の lock 内で pending と timer を潰す。**空文字列分岐が既に行っていることの対称化**で
あり、新しい判断は一つも要らない。決定的なのは、`UiaAnnouncer.cs:55-58` のコメント自身が
危険を言語化していること —— 「pending を残すと SR が古い "2 件目" を読み上げ、視覚(空)と
乖離する」。**コードが欠陥クラスを認識しており、対策が片方の経路にしか入っていない。**

窓外の即時 Raise は「今このメッセージが最新である」という宣言なので、それより古い pending を
残す理由は無い。順序は「lock 内で pending/timer を潰し `_lastSaidUtc` を更新 → lock 外で Raise」
とし、`RaiseAutomationNotification` の I/O を lock で握らない既存方針(`:85-86`)を保つ。

### 3.3 網

`AnnouncerTests.Say_Empty_CancelsPendingTrailingMessage`(`:170`)の直下に同型で 1 本置く。
`FakeTimeProvider` + `RecordingAnnouncer`(`:18`)で §3.1 の表をそのまま駆動できる。

- 修正前: `["a", "c", "b"]`
- 修正後: `["a", "c"]`

**既存の網はこの欠陥を捕まえない**ことを確認済み。`Say_TrailingMessage_IsLastReceived_NotFirstThrottled`
(`:152`)は窓内 Say を 2 回続けるだけで窓外 Say を挟まない。`Say_ThirdCall_AfterTrailingFires_RaisesImmediately`
(`:265`)は trailing が**発火し終えた後**の Say を見るので、armed 中の窓外 Say を通らない。

`_lastSaidUtc` の更新は残す網が別に要る。潰す処理を足したついでに timestamp 更新まで
消しても `["a","c"]` は変わらない(T=70 に何も起きないため)ので、既存の
`Say_ThirdCall_AfterTrailingFires_RaisesImmediately` と `Say_ThrottlesRaise_When50msWithinPrevious`
(`:106`)がその面を押さえていることを実装時に確かめる。

## 4. M-22 — 設定保存失敗でも成功発声

### 4.1 何が虚偽か

`OpenSettings`(`MainForm.cs:1113-1119`)は `SaveSettingsSafe()` を呼んだ直後に**無条件で**
`_announcer.Say("設定を適用しました")` する。`SaveSettingsSafe`(`:1058-1066`)は
`catch { }` で全例外を握るので、保存が落ちても発声は成功のまま出る。

**「適用しました」は半分正しい。** ダイアログ OK 時点で外観適用(`EditorAppearance.Apply`)も
バックアップ設定の反映(`_backup.UpdateSettings`)も済んでおり、走っているアプリには
設定が効いている。落ちたのは**永続化だけ**である。したがって:

- 「設定を適用できませんでした」は**逆向きの嘘**になる(適用はできている)。
- 欠けているのは「次回起動時には元に戻る」という帰結。

### 4.2 設計

`SaveSettingsSafe` を、失敗を返す `TrySaveSettings()`(`Exception?` を返す)へ割る。
**握り潰すラッパ `SaveSettingsSafe()` は残す** —— 呼出は 3 箇所あり、うち 1 つは
`FileController` へ `Action` として渡っていて戻り値を持てないため。

| 呼出 | 位置 | 本設計での扱い |
|------|------|---------------|
| `OpenSettings` | `MainForm.cs:1117` | **`TrySaveSettings` へ差し替え**(本項の対象) |
| `OnFormClosing` | `MainForm.cs:665` | 現行どおり握る(§8 で理由を述べる) |
| `FileController._saveSettings` | `MainForm.cs:207` → `FileController.cs:1575` | 現行どおり握る(§8) |

`OpenSettings` の分岐:

```
var err = TrySaveSettings();
成功 → Say("設定を適用しました")                                    ← 現行文言のまま
失敗 → Say("設定を適用しましたが、保存できませんでした。次回起動時は元の設定に戻ります")
       さらに err が AtomicReplaceFailedException なら、残留 tmp を案内するダイアログ
```

### 4.3 tmp の案内をダイアログにする理由

B4 が実測で確定させた事実(`SettingsStore.cs` の `Save` xmldoc):設定の tmp は
`%APPDATA%\kxEdit\` **直下**に落ち、`BackupStore.SweepTempFiles` を含めどの sweeper の
視野にも入らないため**恒久残留する**。中身は設定で、**最近使ったファイルの一覧(パス)を含む**
(本文は含まない)。

したがって「残っていること」と「消してよいこと」はユーザーへ届けるべき情報だが、
**発声は 1 行のステータスラベルなので長いパスを載せられない**。二段にする:

- 発声 = 短く「何が起きたか」
- ダイアログ = パスと後始末

これは文書保存経路(`FileController.cs:956-976`)が M-12 で採った形と同型である。あちらが
学んだ語順の教訓 —— **SR は線形に読むので、復旧手段を長いパスより前に置く** —— もそのまま
適用する。`SanitizeForDisplay.OneLine` による無害化は外さない(ダイアログ偽装対策の
既存セキュリティ制御)。

**ダイアログを出すのは `AtomicReplaceFailedException` のときだけ。** 通常の失敗
(ディスクフル・ACL)は tmp が残らず案内すべきパスが無いので、発声だけで完結する。
`OpenSettings` は設定ダイアログを閉じた直後なので、ここで MessageBox を出しても
編集を止めない。

## 5. M-20 — バックアップ書込失敗を一度も知らせない

### 5.1 現状の経路

```
SerialBackupWriter.Write の catch (:50-53)  →  OnWriteFailed(record.Id)
  → BackupCoordinator.OnBackgroundWriteFailed (:171)  →  _failed へ Enqueue
    → 次 Reconcile 冒頭の drain (:500-503)  →  該当 DocBackup.ForceWrite = true
      → 次 tick で再書込
```

**この輪のどこにもユーザーへ出る面が無い。** 既定 tick は 300 秒なので、バックアップ先が
書けなくなった(ディスクフル・`%APPDATA%` の ACL 変更・同期クライアントのロック)場合、
ユーザーは**バックアップに守られていると信じたまま**何時間でも編集し続ける。
監査が M-20 を「A-8 の遠因」と書いているのはこの構造を指している。

### 5.2 なぜ「成功の観測面」が要るか

採る方針は**遷移で 1 回だけ発声**(成功→失敗で 1 回、失敗→成功の復旧でも 1 回)。
このうち**復旧側が既存コードでは判定できない**。

`SerialBackupWriter` は失敗しか通知しないため、「失敗が来なくなった」ことしか観測できない。
しかし失敗が来ない理由には「書込が成功した」だけでなく「そもそも書込を投入していない」
(dirty でない・署名一致で `BackupAction.None`)が含まれる。後者を復旧と読むと、
**バックアップが一度も書けていないのに「再開しました」と言う** —— B5 が潰そうとしている
虚偽発声を B5 自身が新設することになる。

したがって `IBackupWriter` に `OnWriteSucceeded`(`Action<string>?`)を足す。
`OnWriteFailed` の対であり、既存の契約・呼出は一切変えない。
`SerialBackupWriter.Write` の try が `BackupStore.Write` から戻った直後に発火する。

### 5.3 遷移の判定

`ReconcileContent` 冒頭の drain(`:500-503`)で両キューを吸い、pass 単位で判定する:

```
anyFailed    = _failed    から 1 件以上取れた   (既存の ForceWrite 設定はそのまま)
anySucceeded = _succeeded から 1 件以上取れた

if      (anyFailed && healthy)      → 失敗を発声 ; healthy = false
else if (anySucceeded && !healthy)  → 復旧を発声 ; healthy = true
```

**同一 pass に両方あれば失敗が勝つ。** 1 文書だけ書けている状態を「復旧」と呼ばないため。
`healthy` の初期値は `true` なので、最初の失敗でも発声する。

`Reconcile` は `Timer.Tick` と `ActiveDocumentChanged` から来るのでいずれも UI スレッド。
発声を UI スレッドへ marshal する追加機構は要らない。

**`WaitForFinalFlush`(`:772`)の `_failed.IsEmpty` は触らない。** あそこが意図的に dequeue
しない理由(終了キャンセル時に `ForceWrite` 再試行が失敗を見失う)は本設計と独立で、
drain の位置も既存のまま `ReconcileContent` 冒頭 1 箇所に閉じている。

`_enabled == false`(レイアウトのみモード)では `ReconcileMapMaintenance` 側へ分岐して
drain が走らないため発声も起きない。**バックアップを書いていないのだから正しい。**

### 5.4 発声面の seam

`BackupCoordinator` に `IAnnouncer` を注入**しない**。`Action<bool>?`(引数 = 健全かどうか)の
フックを生やし、`MainForm` が `_announcer.Say` へ配線する。理由:

- `OnWriteFailed` / `OnLayoutWriteFailed` が既に Action プロパティで、同じ idiom に揃う。
- `BackupCoordinator` は `_map` を非スレッドセーフな Dictionary で持つ UI スレッド専有クラスで、
  発声手段そのものを知る必要が無い。
- Fake を差さずに `Action` を渡すだけで観測できる(既存の `FakeBackupWriter` と同じ軽さ)。

### 5.5 受容する 2 点

**(a) レイアウト書込失敗(`OnLayoutWriteFailed`)は通知面に載せない。**
`session-state.json` が書けなくても、次回起動の復元は `BackupStore.LoadAll` が
バックアップ本体を直接読むので**本文は復元される**。失うのはタブ順とアクティブタブだけ。
監査の M-20 も引用箇所は `Write` の catch であり、レイアウトを含んでいない。
既存の `_layoutForceWrite` による再書込は現行のまま残る。

**(b) 一過性の失敗では「失敗」「復旧」の 2 回鳴る。**
ウイルス対策ソフトが一瞬掴んだだけでも 2 回発声する。ただし tick 既定 300 秒なので
10 分に最大 2 回であり、かつ**その 5 分間はバックアップが実際に効いていなかった**。
黙る側に倒すと M-20 をそのまま残すことになるので、言う側に倒す。

## 6. B4 申し送りの回収 —— `Unreadable` のまま終了すると案内した当のファイルが上書きされる

### 6.1 現状

`SettingsStartup.Prepare` の `Unreadable` 分岐(`SettingsStartup.cs:107-130`)は、退避せず
警告だけ出す:

> 設定ファイルを読み取れなかったため、既定の設定で起動しました。…このまま使うと、
> 読み取れなかったファイルは既定の設定で上書きされます。以前の設定を残したい場合は、
> 先に次のファイルをコピーしてください: `<path>`

その後 `OpenSettings` または `OnFormClosing` が `SettingsStore.Save` を呼ぶと、
**案内した当のファイルが既定値で上書きされる。** 警告文自体は嘘ではない(「上書きされます」と
書いてある)が、ユーザーが後で対処しようとした瞬間に対象は消えている。

### 6.2 却下した案 —— 起動時にコピーを取る

上位の議論では「起動時に自動でコピーを取り、文言を『次の場所へコピーしました』に変える」案が
出たが、**実コードを読むと成立しない。**

`Unreadable` は `SettingsStore.Load`(`SettingsStore.cs:79-95`)で **`File.Exists` が true を
返し、`File.ReadAllText` が投げた**状態である。`File.Copy` は同じ読み取りを行うため、
`ReadAllText` を落とした事由(ファイル単位の DENY ACL・他プロセスの排他ロック・I/O エラー)は
**コピーも同じように落とす**。「コピーしました」と言えるケースがほぼ残らない。

これは「計画のコードは正解ではない」の実例として記録しておく。

### 6.3 採る案 —— 上書きの直前に退避する

`Unreadable` で始まったセッションの**最初の `Save` で、原本を `.bak` へリネームしてから書く**。
リネームに失敗したら、そのまま保存を続ける。

**B4 が退避を却下した理由には抵触しない。** B4 §5.2 の却下理由は「中身が正常なファイルを
改名してしまうため」だが、却下されたのは**起動時**の改名である。起動時点では上書きするか
どうかまだ分からず、ロックが一過性なら次回起動で普通に読めたはずのファイルを改名して
しまう。一方**上書きの直前**なら中身はどのみち失われるので、退避は**厳密に増える側**にしか
働かない。

保存自体は止めない —— B4 §5.5 の判断(止めると「設定を適用しました」が虚偽になる)を維持する。
退避に失敗しても保存へ進む。

### 6.4 文言

起動時の警告を、この機構に合わせて更新する。ただし**退避の成功を約束しない**
(リネームは失敗しうる)。「コピーしてください」という即時の行動指針は残し、退避は
それを補う belt として述べる。具体文は実装計画で確定させる。

`.bak` の掃除はしない。`.bad`(B4 §9)と同じく `%APPDATA%\kxEdit\` 直下でどの sweeper の
視野にも入らないが、**消すのはユーザーの判断**という B4 の方針を踏襲する。文言でその旨に
触れる。

### 6.5 網

`SettingsStartupTests` に seam がある(`quarantineOverrideForTest`)。退避も同型の
テスト seam で注入し、次を固定する:

- `Unreadable` セッションの最初の保存で退避が呼ばれる / 2 度目は呼ばれない
- `Ok` / `Missing` / `Corrupt` セッションでは呼ばれない
- 退避が false を返しても保存は進む(B4 §5.5 の維持)

## 8. 射程外にするもの(理由付き)

上位設計書 §5 の教訓「一括で束ねると Minor ラベルの誤読を再生産する」に従い、項目ごとに書く。

| 項目 | 落とす理由 |
|------|-----------|

### 12.3 ブランチ内で生まれた相互作用(片方向のレビューでは見えなかった欠陥)

M-22 と M-20 は独立に設計・レビューしたが、**両方が同じ 1 行の発声チャネルを使う**ため
互いに打ち消し合う経路が 3 つ生まれた。いずれも**タスク単位のレビューでは見えず、
最終レビューか後続タスクのレビューで出た**。

1. **設定 OK が M-20 の警告を消す** —— `ApplySettings` が `UpdateSettings` 経由で drain を走らせ、
   その中で鳴った警告を直後の `Say("設定を適用しました")` が上書きする。`_backupHealthy` は
   既に `false` なので**二度と報告されない**。
2. **1 の対処が M-22 の失敗発声を消した** —— 「unhealthy なら最後に言い直す」という
   **状態ベース**の条件にしたため、`%APPDATA%\kxEdit` が丸ごと書けない**最もありそうな同時故障**で、
   今度は「設定を保存できませんでした」が丸ごと消えた。**事象ベース**(この呼出で実際に
   フックが撃たれたか)へ直し、同時故障では設定の失敗を**ダイアログへ回す**ことで両立させた。
3. **終端で偽の助言が出る** —— 終了・クラッシュのフラッシュでも drain が走り、
   「ファイルを保存してください」を言った直後に `Environment.Exit` / ウィンドウ消滅が続く。
   しかも同じ pass の `ForceWrite` 再試行が成功すると発声が偽になる。終端では抑止し、
   終了をキャンセルしたときだけ言い直す形にした。

**`UiaAnnouncer` は 50 ms 窓 + `AutomationNotificationProcessing.MostRecent` なので、
1 行の発声チャネルに 2 つのメッセージは載らない。**この制約を設計時に見落としていた。

### 12.5 却下した指摘(1 件)

**`OnWriteFailed` / `OnWriteSucceeded` を `OnWriteCompleted(string id, bool ok)` 1 本へ畳む案**
(Task 3 のコード品質レビュー I-4)。排他不変条件が構造で表現でき、`Delete` へ拡張しやすい、
という指摘自体は妥当。却下の理由:

1. 設計 §5.2 が「`OnWriteFailed` の対であり、**既存の契約・呼出は一切変えない**」と明示している。
2. **`_failed` の意味論は A-8 の hot exit 事後条件検査(`WaitForFinalFlush` の `_failed.IsEmpty`)に
   乗っている。**レビュアーの見積もり(1 行 + テスト 4 箇所)は低すぎる。
3. `bool` 引数は可読性の匂いで、`Action<string>?` が対と揃っている現状の方が読み手に素直。

将来 `Delete` にも結果通知を足す段でコストが顕在化したら、まとめて畳めばよい。

### 12.6 受容した残余

| 残余 | 理由 |
|------|------|
| **一過性の失敗で「失敗」「復旧」が 2 回鳴る** | tick 既定 300 秒なので 10 分に最大 2 回。その 5 分間はバックアップが実際に効いていなかったので言う側へ倒す(§5.5 (b)) |
| **非同期の成功通知による false recovery の窓** | 失敗通知が遅れて届き、前 pass の成功フラグが残っていると誤って復旧と判定。**次 pass で自己修復する**。C-1 が構造として潰したのは「同じ drain に両方届いた」場合で、届く順序のずれは閉じていない |
| **「退避成功 + 保存失敗」で次回起動が無警告の `Missing` になる** | **B5 が自動復旧を 1 つ失わせている** —— B5 以前は保存が失敗しても原本がその名前で残り、ロックが外れた次回起動で読めた。二重障害が要り、データは `.bak` にあり、起動時に予告もしている。**将来案**: `Missing` 枝で兄弟の `.bak` / `.bad` を検出したら 1 行案内する |
| **M-8 が安全メッセージを落としうる窓(最大 50 ms)** | M-8 以前は「古いメッセージが最後に鳴る」(順序が誤り)、以後は「古いメッセージが落ちる」。位置の発声には後者が正しいが、**安全通知にとっては損失**。終了時は A-8 の事後条件検査が silent close を止めるのでデータ喪失には至らない |
| **多重起動で `.bak` が塗り潰される** | `overwrite: false` にすると過去の `.bak` が 1 つ残るだけで退避が永久に効かなくなる(belt が黙って死ぬ)。比較衡量で現行が優る |
| **`.bak` / `.bad` / 設定の tmp を掃除しない** | `.bad` と同じ方針(B4 §9)。**消すのはユーザーの判断** |
| **退避成功後の `settings.json` が原本の DACL を引き継がない** | `File.Replace` → `File.Move` 経路へ移るため。権限は広がる方向だが対象は `%APPDATA%` 配下の自分の設定 |
