# UIA 単語単位の修正 L5 実機 SR 検証チェックリスト

作成日: 2026-08-04
対象ブランチ: `feature/uia-word-unit`
実装計画: `docs/plans/2026-08-04-uia-word-unit-fix.md`
調査結果と修正方針: `docs/plans/2026-08-03-uia-word-unit-design.md`

**L5 は最終ゲート**(CLAUDE.md §5)。本ブランチは SR の読み上げ単位を変える挙動変更なので**必須**である。
`tools/sr-regression.ps1` / `tools/word-sim.ps1` は UIA 応答の検証までで、**実発声は検出できないため
L5 の代替にならない**。

---

## 0. 何が変わったのか(検証者向けの要約)

| # | 変更 | 変更前 | 変更後 |
|---|---|---|---|
| A | **SR が読む単語の規則**(F-3) | 空白 / CR / LF のみが区切り | **文字クラス規則**(Latin / Digit / Hiragana / Katakana / Han / Other の 8 分類)= ダブルクリック単語選択と同じ |
| B | **走査上限**(F-5) | なし(行頭 / 行末まで走る) | **128 code point**。SR / Ctrl+←→ / ダブルクリックの 3 経路が共有 |
| C | expand の窓 | `WordEnd` の起点が `WordStart` の結果 | 起点が**キャレット位置** |

**A の帰結**: 空白の無い日本語行で行全体が読まれていたのが、`今日` / `は` / `晴` / `れです` と刻まれる。
**B の帰結**: 空白ゼロ 500K 行で 1 回の読み上げが約 2.8 秒 → 0.07 ms。ただし**単語が途中で切れる**。
**C の帰結**: 上限が効いてもスパンがキャレットの近くに留まる。

---

## 1. 準備

- **修正前(`main`)でも同じ操作を試せるようにしておく**こと。項目 6 / 11 は**前後比較**が本体である。
- NVDA スピーチビューアーを開く。発話の採取が要る場合は **Win32 `WM_GETTEXT` で全文を取る**
  (`RICHEDIT50W` の `ValuePattern` は**先頭 4096 文字で切り詰められる**ため、そのまま使うと
  1 時間前の発話を読んで「新しい発話が来ていない」と誤判定する。調査時に踏んだ罠)。
- **yEdit は起動引数を受け付けない。** Ctrl+O でパスを打つ。
- windows-mcp は **Insert 修飾を送れない**(`insert+o` が素の `o` になる)。
  NVDA ジェスチャを要する確認は**手動操作で行う**こと。

## 2. チェック項目

### 中核(A = 規則の差し替え)

| # | 操作 | 期待 | 判定 |
|---|---|---|---|
| 1 | `今日は晴れです。` の行で Ctrl+→ を繰り返す | `今日` / `は` / `晴` / `れです` / `。` と**刻まれる**(修正前は毎回行全体) | ☐ |
| 2 | 同じ行で `今` を**ダブルクリック**して選択を目視 → 同じ位置で単語を読ませる | **見える選択と聞くスパンが一致**する(修正前は 2 文字 vs 8 文字)。**SR 無しでも確認できる症状** | ☐ |
| 3 | `foo bar baz` で Ctrl+→ | `bar` / `baz`。**英文の体験が変わっていないこと** | ☐ |
| 4 | `メモ帳のテキストを編集` で Ctrl+→ | カタカナ / 漢字 / ひらがなの境界で刻まれる | ☐ |
| 5 | **★ クラス単位の刻みが自然か**(設計書 §3.3 の未確認事項) | ユーザーの**主観判断**。`今日` / `は` / `晴` / `れです` という刻み方が SR 利用者にとって快適か。**不自然なら規則を再検討する** | ☐ |

> **項目 5 が本ブランチで唯一「実機でしか決まらない」設計判断**である。調査で確認したのは
> 「現状は行全体が読まれる」ことであって、「クラス単位が良い」ことではない。

### 中核(B = 走査上限)

| # | 操作 | 期待 | 判定 |
|---|---|---|---|
| 6 | 空白ゼロ 500K 行(ascii)で Ctrl+← / Ctrl+→ | **発話までの実時間**を測る。修正前は約 1.4〜2.8 秒、修正後は即座。**`main` でも同じ操作を測って前後比較にすること** | ☐ |
| 7 | 同じ行で、上限に当たったときの読まれ方 | run の途中で切れた発話(最大 255 文字)が**許容できるか**。キャレットも単語の途中で止まる | ☐ |
| 8 | **長い空白の連続**(128 文字超)をダブルクリック / SR で読む | 上限は**空白 run の途中でも効く**。上限なしの走査では決して生じない状態なので、体感を見る | ☐ |
| 9 | 空白ゼロ 500K 行(ascii)でダブルクリック → Ctrl+C → 別タブへ貼り付け | **cap で切り詰められた内容がコピーされる**。3 経路で唯一データが欠ける経路。切り詰めが許容できるか / cap=128 が妥当かを**晴眼の視点**で判断する | ☐ |

> **項目 9 の注意**: 3 経路(SR / Ctrl+←→ / ダブルクリック)は**同じ cap を共有**している。
> ダブルクリックだけ緩めたくなっても、それは F-3 の再導入(同じ位置で選択と読み上げが違うスパンになる)
> なので**分けてはならない**。cap 自体を上げるかどうかの判断になる。

### 実装中に発覚した挙動変更(タスクレビューで判明)

| # | 操作 | 期待 | 判定 |
|---|---|---|---|
| 10 | **インデントされたコード行**(`    hello` / `ab    cd`)で、空白の上へ ← → で移動して読ませる | **英文でも変わる位置**。修正前は「キャレット直下の空白 1 個」、修正後は「前の単語」。`ab    cd` の pos=4 では**キャレットの 2 桁左の `ab` が読まれる**。ダブルクリック単語選択と同じ規則なので設計としては一貫しているが、**自然かは実機でしか判断できない** | ☐ |
| 11 | **行末の空白の上**や**空行を挟んだ位置**へ移動して読ませる | **改行を含むスパンが返りうる**。旧実装のスパンは改行を跨げなかった(`a\r\nb  \n  c` の pos=7 で `b  \n` が返る)。NVDA が改行を読み上げるか / 行をまたいで読むか / 沈黙するか。**`main` と修正後の両方で同じ操作を試して差分を見ること** | ☐ |
| 12 | `今日　は`(全角空白)で全角空白の上へ移動 | 全角空白そのものが読まれる(修正前は前の単語 `今日` を読んでいた)。`ClassOf` が U+3000 を `Other` に分類していることの帰結 | ☐ |

> **項目 11 の注意**: PR #35 の L5 で見つかった **E-1(折り返し ON で ↓ を押すと NVDA が「ブランク」)**と
> 紛らわしい。E-1 は `main` でも再現する既存問題なので、**前後比較で切り分ける**こと。

### 回帰(既存機能が壊れていないこと)

| # | 操作 | 期待 | 判定 |
|---|---|---|---|
| 13 | 通常の日本語文書で一通り編集(入力 / 選択 / 検索 / 置換) | SR の読み上げが従来どおり。単語ナビ以外に影響が出ていないこと | ☐ |
| 14 | CSV モード / Markdown プレビューを開いて操作 | 単語規則の変更が波及していないこと | ☐ |

## 3. 繰り越し(本ブランチとは無関係・実機起動のついでに消化できれば)

PR #34 から繰り越されている L5 未検証項目。**本ブランチのゲートではない。**

- **レビューカーソル** — NVDA 修飾キー付きジェスチャ(NVDA+キー)を要する。windows-mcp では送れないので**手動操作**
- **点字** — 点字ディスプレイが手に入ったとき

## 4. 判定と申し送り

- **項目 1〜4 / 6 / 13 / 14 が NG** → ブランチの前提が崩れる。実装へ差し戻す。
- **項目 5 が NG**(クラス単位の刻みが不自然) → **規則そのものの再検討**。設計書 §3.3 へ差し戻す。
- **項目 7 / 9 が NG**(切り詰めが受け入れられない) → **cap 値の再較正**。
  `--wordunit` の掃引表(計画 Task 6)が材料。cap は `WordBoundary.DefaultMaxScan` の 1 定数のみ。
- **項目 10 / 11 / 12 が NG** → 個別に判断。いずれもダブルクリック単語選択と同じ規則なので、
  「SR だけ別扱いにする」ことは F-3 の再導入になる。**規則側を変えるか、受容するかの二択**になる。

結果は PR description へ記録する。NG があった場合は、どの項目がどう NG だったかを
**発話の実物**(スピーチビューアーから採取した文字列)とともに残すこと。
